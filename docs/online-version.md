## 2. 四条约定（违反其中任何一条，症状都是「静默」）

### 2.1 业务失败也是 HTTP 200

`tf-platform-api` 的返回长这样：

```json
{ "code": 607, "error": "scene为必填字段", "data": null }
```

**HTTP 状态码是 200。** 所以 `res.ok` 判断等于没判断 ——
`client.ts` 里唯一有效的判据是 `body.code === 200`。
写成 `if (!res.ok) throw` 的话，所有业务错误都会被当成成功，
`data` 是 `null`，然后在很远的地方炸成「Cannot read properties of null」。

### 2.2 `snake_case` 原样保留

`src/api/types.ts` 里字段名就是 `access_token` / `created_at` / `admin_url`。
**不做驼峰转换**：转一层就要维护一层映射表，而漏一个字段的表现是
「某个数字永远显示 0」，比直接看见 `undefined` 难查得多。

时间戳是 **Unix 秒**，不是毫秒。`humanizeAgo(app.created_at * 1000)`。

### 2.3 手机号在客户端是脱敏的

登录 / 资料接口返回的是 `138****8000`。所以：

- 界面上**只能显示**，不能回填到输入框里当联系方式用；
- 招商申请的 `contact` **必须服务端从账号取**（`merchant_srv.go` 的 `identity()`）。

客户端要是自己拼一个，审核的人拿到的是假号码，而且**没人会发现**。

### 2.4 动作不抛异常，返回 `boolean`

`useAccount` 里 `login` / `register` / `sendCode` 全部返回 `boolean`，
错误写进 `error` 字段。

理由：这是事件处理器里 `void login()` 调用的。抛出去没人接，
控制台一行红字，而**界面上什么反应都没有** —— 用户只会一直点。

## 3. 招商这一条链路（唯一完整闭环）

```
客户端「申请」（只发 role）
   ↓ POST /api/merchant/apply   {"role":"parent"}
服务端 identity() 补 name / contact（昵称 + 账号手机号）
   ↓ 状态 pending
后台 POST /api/admin/merchant/review
        {"application_id":5,"approve":true,"admin_url":"https://..."}
   ↓ 状态 approved + admin_url
客户端 POST /api/merchant/my
   ↓ admin_url **只在 approved 时返回**（服务端抑制，不交给客户端判断）
界面显示「已通过」+「↗ 打开后台」
```

### 3.1 为什么 `admin_url` 由服务端抑制

客户端要是自己判断「这个状态该不该渲染链接」，那么状态判断一错，
用户看到的就是一个写着「已通过」、点进去 404 的按钮 ——
看着像我们把他账号弄丢了。抑制放在服务端，客户端只管「有没有这个字段」。

### 3.2 为什么本地不再存一份

第一版（没有后端时）把申请存在 `settings.merchantApps`。现在删掉了。

两份状态一定会对不上，而对不上的表现是「界面写着审核中、后台其实已经通过了」——
**这种不一致没有任何测试能查出来**，只有用户来问。

### 3.3 未登录时这一屏只做一件事

说清楚为什么登录，给一个登录按钮。**不偷偷存本地假装成功** ——
家长会以为申请已经发出去了，然后一直等。

## 4. 本地怎么跑

```bash
# ① 后端（8080 在这台机器上被别的服务占着，用 8090）
cd tf-platform-api
go build -o tf-api.exe ./cmd/tf-api
TF_LISTEN=127.0.0.1:8090 ./tf-api.exe web      # 注意要 web 子命令，否则打印帮助就退出

# ② 前端
cd kid-quest-farm-2d
npm run build && npx vite preview --port 4401 --strictPort
```

### 4.1 验证码在哪

本地不发短信，验证码打在**服务端日志**里：

```
DEV SMS CODE	{"mobile": "138****8000", "scene": "login", "code": "473325"}
```

⚠️ `send-sms-code` 的 `scene` 是**必填**（`login` / `register` / …），
漏了会返回 `code: 607`。

### 4.2 后台令牌怎么来

`/api/admin/*` 用的是 HMAC 令牌（`X-Api-Token`），不是登录拿的 JWT：

```
base64url( "<unix秒>:<userID>:<hex(hmac_sha256(userID:unix秒, AdminSignKey))>" )
```

`AdminSignKey` 在 `configs/config.yaml`（该文件不进 git）。

### 4.3 验收命令

```bash
# 契约测试（真连服务端；默认 skip）
VITE_LIVE_API=1 npx vitest run src/api/live.test.ts

# 界面走查（真登录 + 真申请 + 拿界面状态去对服务端状态）
node scripts/_probe-online.mjs http://127.0.0.1:4401/ 390 844
node scripts/_probe-online.mjs http://127.0.0.1:4401/ 834 1112
```

⚠️ `_probe-online` 断言的是「**界面显示的状态 == 服务端返回的状态**」，
不是「点完一定显示审核中」。写死后者会在账号已被审过时假红，
而人第一反应是「我改的代码坏了」。

## 5. 游戏激活码这一条链路（2026-10-30）

家长在淘宝/天猫/京东买到游戏卡 → 卡背面一串激活码 → 输进
**设置 / 游戏 / 有兑换码？** → 服务端验码并授予游戏 → 那款游戏从
「心愿商城」消失、在「我的游戏」里变成已拥有。

```
心愿商城（家长确认页）
  └─ 「↗ 去商店购买」→ openExternal(buy_url)     ← 装了淘宝就直接进淘宝
        ↓ 家长自己付款，卡到手
设置 / 游戏 / 有兑换码？
  └─ redeemGameCode(code)
        ├─ 登录了  → POST /api/wish/redeem-code   ← 真相在服务端
        └─ 没登录  → 本机码表（离线 / 单测）
              ↓ 服务端一个事务里：验码 → 标记已用 → 写 user_game
        本地补一笔账本（source=redemption_code, delta=0）→ ownedGameIds 认它
              ↓
        插件包 installLocalGame(gameId)  → 装好就能玩
```

### 5.1 为什么本地还要补一笔账本

`ownedGameIds` 是从本地账本推的（`purchasedIdsFrom`），不是从服务端拉的。
服务端给了游戏但本地不记这一笔，「我的游戏」里就不显示已拥有 ——
而服务端明明已经给了。**delta 必须是 0**：码解锁一分钻石都没花。

### 5.2 三个「必须分开说」的失败

| 情况 | 家长该做什么 | 文案必须说明 |
| --- | --- | --- |
| 连不上服务器 | 过会儿再试 | **这张码没被用掉** |
| 登录过期 | 重新登录 | **这张码没被用掉** |
| 码无效 / 已用过 / 已过期 | 别再试了，找卖家 | 照抄服务端文案 |

合成一句「兑换失败」，前两种情况下家长会以为卡废了，再去买一张。

### 5.3 装包失败 ≠ 兑换失败

码已经在服务端用掉了，客户端回滚不掉。所以装包失败时**不能报失败** ——
报失败会让人以为码没用上。照实说「已激活，但没装成功，去「我的游戏」里点安装」：
已拥有是有出口的（点安装就行），码没了才是没出口。

### 5.4 服务端修掉的两个坑

1. **先判「是不是已经有了」再烧码**。原来是先 CAS 标记已用、再
   `ON CONFLICT DO NOTHING` 授予 ⇒ 孩子早就有了那款游戏时，码被烧掉、
   什么都没换到，界面还显示「兑换成功」。现在返回 `game-already-owned`
   （「你已经拥有这个游戏了」），码保留。
2. **`user_game.created_at` 落 0**。平台 `BaseModel` 是 `autoCreateTime:false`，
   四个授予点都没手写时间戳。已收进 `stampGrant()` 统一补。

### 5.5 APK 上的外链

`window.open` 在 Capacitor WebView 里**不生效**（没有地址栏、没有新标签页），
表现是「点了没反应、零报错」。走 `src/platform/openUrl.ts`：

- 原生 → `AppLauncher.openUrl()`（Android `ACTION_VIEW` / iOS `UIApplication.open`）：
  装了淘宝且它认领了该域名 ⇒ 直接进 App；否则落浏览器。
- Web → `window.open(..., 'noopener,noreferrer')`。

`javascript:` / `data:` / `file:` 一律拒（第二道闸，服务端那道不代替这道）。

> ⚠️ 加了原生插件 `@capacitor/app-launcher@8.0.1`，**打 APK 前要 `npx cap sync android`**，
> 否则原生侧没有这个插件，`openUrl` 会走 catch 落到 `window.open`（等于没修）。

### 5.6 装包要过「已拥有」这道门（2026-10-30 起）

原来 21 款随包游戏在「我的游戏」里**全部能免费点安装** —— 于是激活码在设置页
看不出任何区别：激活前也能装，激活后也一样。现在 `installLocalGame` 先判拥有，
没拥有时那一格显示「去心愿商城」，不摆一个点了才告诉你「还没拥有」的按钮。

「拥有」有**三个来源**，收在 `wishOwnedSet(ownedGameIds, installedGames, wishOrders)`：

| 来源 | 什么时候有 |
| --- | --- |
| 本地账本 `game_purchase` / `redemption_code` | 用钻石买 / 用激活码解锁 |
| 已装包 `installedGames` | 加门槛之前就装上的（**不能因为加门槛把它们锁死**） |
| 心愿单 `openedGameId` | 心愿商城换到并已开箱 |

⚠️ 只按账本判会把「心愿商城换来的游戏」一起锁死 —— 那批订单不写 `game_purchase`。

⚠️ `installLocalGame` 里的判定**读库不读 store 快照**：兑换流程是
「先记账本 → 再装包」，同一轮里 store 还没刷新，读快照会把刚兑换的判成没拥有。

e2e 里点安装前要先 `await grantGame(page, GAME_ID)`（`scripts/lib/own.mjs`，
走 `window.__kqf__.grantGame`）—— 21 个脚本已统一加好。

### 5.7 输码口搬到了商品详情页（2026-11-05）

用户原话：「为啥 游戏 盲盒 还有 游戏 都没有 激活 的地方。应该在心愿商城
对应 item 就可以激活吧。不然拿到了 激活码 或者兑换码，咋办。」

在那之前全 App 只有两个输码口，而且**都在家长区**：

| 位置 | 谁能到 |
| --- | --- |
| `设置 → 游戏 → 有兑换码？` | 家长（三层菜单 + 家长锁） |
| 心愿商城 · 家长定价页 | 家长（先过密码，再点「定个价」） |

孩子手里捏着一张卡、站在**卖这张卡的那件商品**上，却无处可输。

现在 `WishPage` 的商品详情页多了一块 `已经买到卡了？`（`data-wish-code`），
和定价页共用同一个组件 `features/wish/CodeRedeemBlock.tsx` —— 一份实现，
两处挂载，不存在两套口径。差别只有闸门：

- 详情页 `gate="pin"`：**保护开着时先过家长密码**（码是花钱买的，
  激活之后退不回来；用户选的是「保持现状（家长控制）」）。
- 定价页 `gate="open"`：整页已经在闸门后面，不必连输两次。

⚠️ **成功之后不切当前游戏**。和 `purchaseGame` 同一条口径：买完不自动切，
切「当前」是家长在 `设置 → 游戏` 里的显式动作。成功块里只写一句指路。

⚠️ **「已拥有」的判断在组件内部，别写回调用方的 `!alreadyOwned &&`。**
激活成功会立刻 `refresh()` ⇒ `alreadyOwned` 变 true ⇒ 条件渲染会把整块
（连同「✅ 已激活」）在同一帧卸载 —— 表现是「码用掉了、游戏到账了，
界面上什么都没说」，看着像点了没反应。组件里用 `return null` 不卸载实例，
`msg` 才留得住。2026-11-05 用**真码**走查抓到的（假码只验到「服务端报错」，
happy path 一行都没走过）。

⚠️ 盲盒**没有**输码入口，页面会明说「盲盒没有激活码」：它开的是随机一款，
走的是兑换券（`wishRedeem`），硬塞一个输码框只会让人以为盲盒也能用码开。

验收（三条走查，`scripts/` 下，**都不入库**）：

| 脚本 | 验什么 |
| --- | --- |
| `_probe-wish-code-ui.mjs` | 入口在不在、保护开着先出密码、假码拿到服务端中文错误、盲盒页的说明 |
| `_probe-wish-code-happy.mjs <码>` | **真码** happy path：绿字留下 → 进 `ownedGameIds` → 回列表该卡片消失 |
| `_probe-wish-code-gate.mjs <码>` | 家长锁开着：答加法 → 第一次设密码（两遍）→ 输码 → `设置 → 游戏` 不再是「未拥有」 |

真码用 `tf-admin/scripts/_gen-test-code.mjs` 现生成（调 `POST /mall/wish/code/generate`）。
⚠️ 局域网是 http（非安全上下文）⇒ 没有 `crypto.subtle`，插件包验签必然失败，
界面会照实写「已激活，但没装成功」—— 那不是 bug，APK 里是安全上下文。

## 7. 第二期：写穿（2026-11-02）

第一期只做了「读」（登录后把服务端拉进 Dexie）。写还在本地，
于是 `VITE_APP_MODE=online` 的包其实是「看得见云端、改的是本机」——
换台设备就发现白改了。这一期把**任务这一整条**改成写穿。

### 7.1 形状

```
界面 → store 动作 → if (isOnlineMode) → online/*.ts → src/api/* → tf-platform-api
                                      ↓ 成功
                                   refresh()（重拉）→ Dexie → 界面
                                      ↓ 失败
                            toast「没发出去，刚才那一步没有生效」+ **什么都不写**
```

`src/online/` 三个文件：

| 文件 | 职责 |
| --- | --- |
| `ids.ts` | 本地 id ↔ 服务端数字 id（`srv_task_12` ↔ `12`） |
| `write.ts` | `onlineWrite()` 把「调接口」收成 `{ok, data} / {ok, error}`；`writeFailToast()` 翻成人话 |
| `tasks.ts` | 一对一映射 store 动作；`camelCase → snake_case` 只有一张表 |

### 7.2 三条铁律

1. **失败绝不落本地。** 先存本地再补传的话，孩子看到「交上去啦」、
   家长永远收不到，而两边都不报错。写穿的整个价值就在这一条上。
2. **写完不自己算，`refresh()` 重拉。** 结算规则在服务端
   （`task_settlement.go`），本地再算一遍 = 两份真相。
3. **单测跑本地模式。** `vitest.config.ts` 里 `define` 把 `VITE_APP_MODE`
   钉成 `local` —— 否则 1067 条用例全都会去发 HTTP，失败信息还是
   `fetch is not defined`，看起来像环境问题。

### 7.3 三个「服务端没这个语义」的地方

| 客户端动作 | 服务端的现实 | 在线版怎么办 |
| --- | --- | --- |
| 提交后**立即结算**（家长关掉了审核） | `/task/submit` 一律进 `submitted` | 紧接着自己调一次 `/task/review` 通过，把语义补回来 |
| **签到审核**（`approveCheckIn` / `rejectCheckIn`） | 服务端签到**一步做完**，`NeedReview` 恒 false | 在线版不会有待审条目，这三个动作自然没被点到 |
| 连签**阶梯领奖**（`claimCheckInTier`） | 服务端自动发（`claimed_tiers`） | 同上，界面不会出现「领取」按钮 |

### 7.4 边界在哪：哪些东西**故意**没上云

到 §7.13 为止，八块业务数据全是写穿。换设备之后：

- 任务、今日任务板、积分、流水 → 一致 ✅
- 农场（地块 / 动物 / 背包 / 行情 / 额度）、兑换券 → 一致 ✅
- 兑换商城（商品、兑换记录、兑现状态）→ 一致 ✅
- 心愿商城（家长定价、心愿单、已取消的回绝原因）→ 一致 ✅
- 游戏币（余额 / 买 / 玩 / 铸 / 换券 / 发券）→ 一致 ✅
- 插件存档（`/game/kv/*`，见 §7.13）→ 一致 ✅
- **家长设置**（含新手引导进度 `onboardingStartHour`）→ 各设备各一份 ❌
- **设备本地状态**（PIN、今天玩了多久、音效 / 震动开关）→ 各设备各一份 ✅

最后两类**不是「还没做」**，是语义上不该同步：它们描述的是「这台设备 / 这位家长」，
不是「这个孩子」。判据只有一句话 —— **换一台设备之后，你希望它变吗？**
「孩子的农场」希望一致；「今天已经玩了多久」希望各算各的（否则孩子换个设备
就能重置时长限制）。所以这两类不但不上云，导出备份时还要**剥掉**。

> ⚠️ 游戏币上云之后，`gameKv['__coin']` 在在线版里**不再是账本**，
> 而是「服务端余额的镜像」（单行，`delta` 就是余额）。
> 为什么这么做、以及为什么不敢做成「每次现问服务端」：见 §7.12.1。

> ⚠️ **商品目录仍然不在服务端**：`wish_item` 那张表是
> `games/wishCatalog.ts` 常量在库里的**副本**（`seed/wish_catalog.go` 写入），
> 用途只有「定价 / 兑换时查得到这件商品」。界面渲染读的是常量 ——
> 两条目录并存的前提是 **id 完全一致**，见 §7.11.1。
>
> ⚠️ 「兑换券的真相」已经定了：**服务端**。卖菜得多少券仍然是本地算的
> （行情 / 额度 / 品质都在 `src/domain/`），但**记到哪儿**由服务端决定 ——
> 客户端把「这次该加多少」作为 claim 随状态一起提交（同一个事务、幂等键
> `op_id`），本地账本从「账本」降级成「服务端流水的镜像」。
> 细节和它带来的四条新约束见 §7.7。

### 7.5 农场接口（2026-11-02 起客户端已接）

```
POST /api/farm/state/get   → { empty, rev, payload, updated_at }
POST /api/farm/state/save  → { conflict, rev, applied, balances }
       body: { payload, rev, ledger?: [{currency, delta, source, memo, op_id}], force? }
```

- `payload` 是**整块 JSON**（地块 / 动物 / 背包 / 行情 / 世界日 / 额度结转 / 事件）。
  服务端不理解玩法，只负责「谁的那一份」。
- `rev` 是乐观锁：两台设备同时改，后到的拿 `conflict=true`，**什么都没写**。
- `ledger` 是随状态一起提交的币变动，**同一个事务**入账 ——
  拆成两次请求的话，中间断网就是「菜没了、券没到」。
- `op_id` 是幂等键（服务端拼 `farm:<uid>:<op_id>`），重试 / 连点不会多给一次。
- `source` 有白名单（`farm_harvest` / `animal_produce` / `seed_purchase` /
  `animal_purchase` / `plugin_mint`）：账本来源是给家长看流水的，
  客户端不能把自己的消费记成 `task_reward`。

验收：`node scripts/_probe-farm-state.mjs`（12 条，可反复跑）。

## 7.7 第三期：农场上云（2026-11-02）

农场是**唯一一块「玩法全在客户端、状态又必须整块一致」**的数据：
作物、动物、背包、行情、额度结转、世界日，全都互相咬着。
搬去服务端有两条路，这一期选了后者：

| 方案 | 代价 |
| --- | --- |
| 把玩法搬到 Go | `src/domain/` 那 1000+ 条单测要重写一遍，而且从「一份规则」变成「两份规则」 |
| **整块 JSON + 乐观锁**（选了这个） | 服务端不理解内容，只能做「谁的那一份」和「别同时写坏」 |

### 7.7.1 形状

```
界面 → store 动作 → if (isOnlineMode) → runFarmCommit()
                                        ├─ 先跑本地那套算法（一行没改）
                                        ├─ 读回整块 payload + 这次产生的账本变动
                                        └─ POST /api/farm/state/save（一个事务）
                                              ↓ 成功            ↓ 失败 / 版本冲突
                                          refresh()（重拉）   恢复动作前的快照 + 提示
```

四个文件：

| 文件 | 职责 |
| --- | --- |
| `src/online/farm.ts` | payload 读写、`/farm/state/*`、账本暂存（sink）、rev |
| `src/db/db.ts` | `setLedgerSink()` —— 动作期间把 `postLedger` / `postHarvest` 接管掉 |
| `src/store/useApp.ts` | `runFarmCommit()` 外壳 + 10 个农场动作开头那三行守卫 |
| `src/sync/pull.ts` | 顺带把服务端 `coupon` 币种的流水拉进 `harvestLedger`（镜像） |

### 7.7.2 payload 里有什么、没有什么

**有**（少一个的症状都是「换台设备某样东西回到初始值」，且不报错）：
地块、动物、背包、行情、额度结转、三项累计统计、世界日。

**没有**，而且是有意的：

- `farmEvents`（农场日志）—— 它是给人看的历史，不是状态。塞进整块 blob
  只会让两台设备互相覆盖对方的日志
- `farm.lastEventCheck`（生病事件的检查点）—— 设备本地的节流阀
- 家长设置（`settings`）—— 这一期不在范围内，见 §7.4

### 7.7.3 账本：**根本不写本地**，而不是「写完再删」

这是这一期最关键的一处取舍。

`runFarmCommit` 在跑动作之前调 `beginFarmTx()`，它把 `db.ts` 里的
`ledgerSink` 装上。于是动作期间 `postLedger` / `postHarvest` **不写 Dexie**，
只把这一笔记成一条 claim，等着一并提交。动作结束（`endFarmTx`）后钩子摘掉。

为什么不「先写本地、提交成功再删」：

- 删的那一下出问题（断网、崩溃、并发的拉取），本地就多出一笔服务端没有的账
  —— **余额虚高，而且永远不会自己恢复**
- 反过来「先提交、再补写本地」也不行：补写失败就是「服务端有、界面没有」，
  孩子会反复点同一个按钮

只有「**根本不写**」没有这两个状态。服务端那份由紧接着的 `refresh()` 拉回来。

> 0 元的行（`feedAnimal` 那条 `farm_feed` 备注）不受影响：它没有金额，
> 照常落本地，所以「喂过鸡」这件事不会从流水里消失。

### 7.7.4 服务端白名单要在客户端镜像一份

`tf-platform-api` 的 `farmClaimSources` 只认八个来源。客户端
`FARM_CLAIM_SOURCES` 是它的**逐字镜像**。

为什么要多这一层：白名单外的来源发上去，服务端会**整笔拒绝**（`10110301`），
连农场状态一起存不上 —— 一个只影响流水标签的小问题，会表现成
「点一下收获，什么都没发生」。

### 7.7.5 服务端那份脏了，客户端要能治好它

`parseFarmPayload` 解析失败时**保留本地那份**（不清空、不回初始农场），
但**仍然把 `rev` 记下来**。

第二句是踩出来的：不记 rev 的话，下一次提交会拿 `rev=0` 去写，
服务端回 `conflict`，孩子点什么都提示「农场在别的设备上改过」——
而真正的原因只是服务端那份读不懂。记住 rev 之后，下一次提交会把
一份好数据覆盖上去，**自愈**。

`_probe-farm-online.mjs` 第 1、2 组断言的就是这个：先往服务端写一份
「不是农场」的 payload，再启动 App，断言①本地农场原样保留 ②启动后
服务端那份已经被换成一份真农场。

### 7.7.6 四条新约束（违反的症状都不明显）

1. **背包在在线版归农场所有。** 拉取是**整表替换** `db.inventory`。
   将来有非农场路径（兑换奖励、心愿发货）往背包里塞东西时，必须
   **同时**把它放进 payload 一起提交，否则下一次拉取会把它抹掉 ——
   而界面上只会表现为「刚才换的东西不见了」。
2. **动作成功的那句 toast 可能跟着一句失败 toast。** 本地算法先跑
   （那是它自己的反馈），提交失败后还会补一句「刚才那一下没发出去」。
   这是写穿的代价，不是 bug：宁可多一句，也不要「看着成功、其实没存」。
3. **连点没反应的动作不会打请求。** `runFarmCommit` 会比对动作前后的
   payload，没变化且没有账本就跳过提交 —— 点还没熟的菜、没肥料时点施肥，
   都不该推进 `rev`。
4. **旧设备上的兑换券余额只在本机。** 从本地版升级上来的账号，
   `harvestLedger` 里那些 `hv_` 行不会被搬到服务端（服务端余额从 0 起），
   所以「本机余额 = 旧行 + 云端行」。要真正搬过去得加一个服务端的
   「期初结转」来源，并重写历史 —— 这一期**没做**，先记在这儿。

### 7.7.7 验收

```bash
node scripts/_probe-farm-online.mjs http://127.0.0.1:4405/   # 25 条
```

它真连 `tf-platform-api`、真在浏览器里点，断言的是「**界面 == 服务端**」：

- 服务端那份是脏的 → 本地农场没被清空，且随后被治好
- 播种后**服务端的地块上真的有这棵萝卜**，`rev` 推进

- 卖出后**服务端兑换券加了同样多**，本地余额也对得上
- 断网时 `plant` 返回 `false`、地块还是空的、积分没扣、服务端 `rev` 不动

`assets/index-*.js`，和 `dist/index.html` 比。这台机器上 4401/4402 常年被
别人的 preview 占着，`--strictPort` 起不来但 `curl` 照样 200。

## 7.8 新用户进门：自动游客账号（2026-11-03）

### 7.8.1 为什么把登录闸门拆了

2026-11-02 做的是**全屏登录闸门**（`OnlineLoginGate`）：没登录就盖一层，
说清楚「数据在云上」，给一个登录按钮。

新用户反馈：**没耐心，一进来就要注册登录**。而且当时的闸门不是「有点烦」，
是**真的进不去**：

| 入口 | 当时的状态 |
| --- | --- |
| `/auth/register` | 要 6 位短信验证码，而 `DevSmsSender` **只把码打进日志** |
| `/auth/sms-login` | 同上 |
| `/auth/wechat-login` | `wechat.AppID` 是空的 ⇒ 换 code 必失败 |

也就是说，除了「后台手工造一个号」，**没有人能注册进来**。闸门后面是一扇
锁着的门。

### 7.8.2 现在的做法

启动时**自动建一个游客账号**（`POST /api/auth/guest`，按设备号建号或取号），
孩子不用注册、不用等验证码，进来就能玩。

```
启动 → ensureGuest()（拿账号）→ boot()（拉数据）
```

★ **顺序不能反。** `boot()` 里第一次 `refresh()` 负责把服务端数据拉进 Dexie，
没有会话时它直接返回 `no-session`，一条都不拉 —— 孩子看到的是一整套空界面，
而屏幕上什么都不会说。这一句写在 `App.tsx` 的启动 effect 里。

### 7.8.3 ★★ `user.mobile` 必须加 `default:null`

游客没有手机号，而 `mobile` 上有**唯一索引**。GORM 对「没有 `default` 的
string 零值」会老老实实写 `''`，于是**第二个游客**直接撞唯一索引：

```
UNIQUE constraint failed: user.mobile
```

现场表现是「第一个人能进，第二个人一进来就报错」，而且接口只回一句
`operation-failed`（`isDuplicateKey` 被包成了通用错误），日志里什么都没有。

加上 `default:null` 之后，零值走「省略该列」⇒ 落库 NULL ⇒ SQLite / MySQL 的
唯一索引都允许多个 NULL，而真手机号的唯一性一点没松。

判据是 Go 单测 `TestGuestLoginTwoDevicesCoexist`。做过变异验证：
把 `default:null` 去掉它立刻变红。

### 7.8.4 ★★ 会话过期之后不许偷偷换账号

`refresh_token` 只活 7 天。一个「一周开两次」的家长，很容易撞上会话过期。
这时候如果无脑建游客，等于**把人悄悄换成一个空账号** —— 他的任务、积分、券
都还在原来那个账号里，而屏幕上是一片空白。他会以为数据没了。

所以 `api/lastAccount.ts` 单独记一份「上一次是谁」：

| 上一次 | 会话过期之后 |
| --- | --- |
| 游客 | 自动建回来（同设备号 ⇒ 服务端返回同一个 uid，进度一点不丢） |
| 正式账号 | **不建游客**，转成 `needs-login`，弹 `LoginSheet` 请他登回来 |
| 不知道（全新安装） | 当游客处理（这正是「没耐心」的那批人，不能拦） |

退出登录**不清**这两个标记：退出的意图是「换个人」，之后启动仍然请他登录。
真要「不登录先玩」，登录面板底部有一个显式的「先随便玩玩（不保存）」，
它走 `ensureGuest({ force: true })` —— 跳过上面那道判断，是**用户自己的选择**。

### 7.8.5 硬门槛放在钱包层，不放在按钮上

游客能花**积分**（买种子 / 动物 / 游戏 —— 拦了等于不能玩），但**不能花兑换券**
（那是要落到现实里的东西）。服务端返回 `10010802 guest-need-bind`。

拦的位置是 `WalletService.Change` / `ChangeWithTx` —— 所有扣币的唯一入口。
放按钮上不行：花券的地方有五处（兑换商城、心愿单、币换券、游戏内消费、农场
提交的账本），以后还会加，漏一处就是「游客把券花掉了」，而券是家长真金白银
换来的，漏了没有任何界面会露出来。农场那条直接写仓储，单独挡一次。

客户端在 `api/client.ts` 里挂了一个 `bindGuestBlocked` 钩子：任何接口返回这个码
就弹「保存进度」。挂在钩子上而不是每个调用点，理由同上。

> ★ 这一跳（服务端码 → 拦截器 → `onGuestBlocked` → 面板）原来**没有任何测试**。
> 服务端单测证明了「会拒」，界面单测证明了「面板能开」，中间那根线断了，
> 两边照样全绿 —— 而现场表现是「点了兑换，转一圈，什么都没发生」，界面上
> 一个字的线索都没有。`api/client.test.ts` 现在钉了四条：这个码要**弹**并且
> 照常抛错（调用方还要靠它提示「这次兑换没生效」）、别的码**不能**弹
> （「余额不足」不该说成「先绑定手机号」）、401 也不能弹（那是登录过期，
> 另有出口）、回调能注销（模块级变量不清，测试之间会互相串）。

### 7.8.6 提醒时机：只剩「花券被拒」和「自己点」（2026-11-05 改）

| 时机 | 形态 | 会不会重复 |
| --- | --- | --- |
| 第一次花兑换券（被服务端拒） | 弹面板，**没有「以后再说」** | 每次都弹（这不是提醒，是解释） |
| 自己点设置页顶栏的账号胶囊 | 弹面板，可以关 | 只在用户点的时候 |
| 进家长区（设置 → 规则） | 账号卡上写「临时账号 · 保存进度」 | 常驻（那一页要过 PIN） |

> ★ 2026-11-05 删掉了两个「主动开口」的时机：顶栏下面那条常驻横条
> （`GuestBar.tsx`）和第 3 次启动的自动弹窗（`guestPrompt.ts`）。用户原话：
> 「临时账号.换手机或清除数据就找不回 保存进度 这个感觉可以不要吧
> （任务不是 后端有记录 用户的任务吗？）」
>
> 事实是：进度**确实**在服务端（`task` / `redeem_item` / `wallet` 都按 uid 存），
> 丢的只是那串设备号（`api/device.ts` 的 `kqf.device.id.v1`）。但「会丢」
> 这句话本身没错 —— 清数据 = 新设备号 = 新账号，服务端那份从此进不去。
> 所以删掉的不是「事实」，是**说法和频率**：不再天天在顶栏上吓人，也不再
> 替用户决定「该存了」。入口留在设置页顶栏那个胶囊上（游客时是按钮，
> `data-guest-save`），家长想存的时候一步就能到。
>
> ⚠️ 删掉的东西**不要**被「好心」加回来：横条看起来贴心，但它说的
> 「只在手机上」在在线版里是错的，而且它会占掉顶栏下面那一行 —— 孩子每天
> 看到的第一条信息变成一句催办。

为什么「第一次挣到积分」也不弹窗（这条仍然成立）：那一刻孩子正在庆祝
（任务通过 / 签到成功），弹表单会打断他，他多半直接点掉 —— 这次机会就浪费了。
（原来还有「横条上的字变成已攒 N 分」这个折中，横条删掉之后这条也一起没了。）

### 7.8.7 常驻入口为什么在设置页，不在顶栏

顶栏那一行已经挤满了（头像 + 名字 + 三颗币 + 两个按钮），`App.tsx` 里那段
注释写着「这一行的余量已经用完了」。原来把「临时账号」横条放在顶栏**下面**，
不抢横向空间；2026-11-05 横条整条删掉之后，入口挪到了**设置页标题栏的胶囊**：
游客时它是 `button`（`data-guest-save`），正式账号是纯文字。

⚠️ 那个胶囊**不能**挂 `data-account-open` —— 走查脚本拿它判「还没登录」，
游客是有账号的，挂上去会让脚本永远判「需要登录」。

### 7.8.8 原来的闸门在新手引导**下面**（历史）

全新设备上先出现的是本地那一步（起小名 / 选头像 / 家长密码），走完才轮到
闸门。两个都是 `fixed inset-0 z-[60]` 的 Portal，DOM 里后出现的在上面 ——
所以闸门被引导盖住。

⚠️ 验证时**不能用 `el.click()`**：它不走命中测试，会在「被盖住的按钮」
上成功，让人以为验过了。2026-11-02 第一版检查脚本就是这么假绿的 ——
换成 `document.elementFromPoint(中心点)` 才看出命中的是引导，而不是闸门。
真实用户的路径是「先走完引导，闸门才露出来」，所以脚本里也要先
`updateSettings({ onboardingDone: true })` **再重载**（引导的闸门是启动时
决定一次的，运行中改设置摘不掉它，见 `App.tsx` 的 `gateDecided`）。

### 7.8.9 ★★ 「再试一次」必须连账号一起重试（2026-11-03 补）

拆掉闸门之后，启动路径变成 `ensureGuest()` → `boot()`。如果**这一刻**连不上
服务器（地铁里、电梯里、第一次打开就弱网），建游客就失败了 ——
结果是**整台设备一个令牌都没有**，界面照常打开，但农场是空的。

坑在重试按钮上：`SyncBanner` 原来只调 `useApp.refresh()`（重拉数据）。
没有令牌 ⇒ 拉取照样失败 ⇒ 横条一直在、界面永远是空的，**而且不报错**。
唯一的出路是重启 App，而人不会想到要重启 —— 他只会说「这 App 是坏的」。

所以按钮改成「先确认有没有账号，再拉数据」：

```ts
if (!hasSession) await ensureGuest()   // 幂等：有会话就立刻返回
await refresh()
```

判据不看「按钮有没有反应」，看**调用顺序**（`guest` → `refresh`）。
`src/components/SyncBanner.test.tsx` 里那条断言就是这个顺序；变异掉
`await ensureGuest()` 会精确地让它变红（其余三条仍绿）——
「只红该红的那条」才算测到了点子上。

同类还有一处：`useApp` 里 `no-session` 原来被当成「正常，别报警」，
现在**算失败**。理由一样 —— 闸门没了之后，「没有会话」不可能再是
「等用户登录」，只能是「服务器没连上」，那就不该安静。

### 7.8.10 平板尺寸（`_probe-guest-tablet.mjs`）

手机竖屏（390×844）过了不等于大屏过了。两块界面里，设置页那个账号胶囊在标题栏里、
面板是 Portal 到 body 的覆盖层，各有一种专属的翻车形态：

| 尺寸 | 查什么 | 为什么 |
| --- | --- | --- |
| 1024×768 / 768×1024 | `scrollWidth > innerWidth` | 竖屏平板最容易被 `min-w` / `whitespace-nowrap` 撑出去，`overflow-x-clip` 把超出的部分**裁掉**（不报错，就是看不见） |
| 同上 | 面板矩形是否整块在视口内 | Portal 的层没写 `max-h` 时会顶出屏幕，底部「绑定并保存进度」就点不到 |
| 同上 | `elementFromPoint` 命中按钮 | `el.click()` 不走命中测试，被盖住也照样「成功」 |

实测两种尺寸都是 18/18 通过：面板 640px 居中、按钮全在视口内、无横向溢出。
**没有发现布局问题** —— 但这一轮排查本身抓到两个探针自己的坑：

1. ★★ **同一次浏览器会话里连开两个页面 ≠ 两个新用户**。`localStorage` 是共享的
   ⇒ 设备号被复用 ⇒ 第二个尺寸拿到的是**同一个游客账号**，还会继承上一个尺寸
   留下的面板 / 设置页状态。第一版就是这么红的，看着像「胶囊点不到」。
   ⇒ 每个尺寸用 `browser.createBrowserContext()` 单独一个上下文。
   （当时还有一个 `openBind('launch')` 会在第 3 次启动自动开面板，
   2026-11-05 已删；但独立上下文这条仍然必须保留。）
2. **面板刚出现的那一两帧点不到**：`anim-sheet-up` 是从屏幕下方推上来的，
   此时可点区域还在视口外，`page.click` 直接抛
   `Node is either not clickable or not an Element` —— 像「按钮坏了」。
   ⇒ 等 600ms 再点。★ 顺带说明 `page.click` **是**带命中测试的，
   这一点比 `el.click()` 可信。

### 7.8.11 ★★ 没有短信通道时怎么绑（验证码可选，密码必填）

**事实**：`DevSmsSender` 在 `IsProduction()` 下直接返回错误
（`sms sender not configured for production`），验证码根本发不到手机上。
也就是说「必须填验证码才能绑」= **永远绑不上**，游客攒的东西一辈子存不下来。
这个问题一直存在，只是以前被全屏登录闸门挡着，没人走到这一步。

现在把验证码改成**可选**，但补了一条更硬的约束：

| | 填了验证码 | 没填验证码 |
| --- | --- | --- |
| 密码 | 可选 | **必填** |
| `mobile_verified` | `true` | `false` |
| 能不能绑 | 能 | 能（号码得是没人用过的） |

**为什么密码变成必填**：两者分工不同 —— 验证码证明「这个号是你的」，
密码是「以后怎么回来」。两个都不给，这个账号换台手机就永久丢了，
而且丢的时候不会有任何提示。服务端也拦这一条（`bind-need-password`
= 10010803），不只是界面上的约束。

**为什么放宽不会变成「随便抢号」**：`MobileAlreadyReg` 那道检查还在，
所以不带验证码最多能绑到一个**谁都没用过的空号**，动不了别人的账号。
`probe-guest.py` 的 [7.4] 就是守这条的。

**注册同一口径**：`/auth/register` 的 `code` 也改成可选了（密码本来就是必填，
所以「回来的路」天然存在）。界面上注册那一栏写着「验证码（收不到也能注册）」，
但**「重设密码」仍然必须填码** —— 那条路唯一的凭证就是验证码，放开等于谁都能改密码。

**忘了密码怎么办**：`/auth/reset-password` 仍然要验证码（那条路唯一的凭证就是码），
所以 C 端自助重置走不通。兜底放在**后台**：`tf-admin` 的「App 用户」页里有一个
「重置登录密码」—— 客服核实身份后点一下，服务端生成一次性密码（8 位，去掉了
`0/O`、`1/l/I`），写 bcrypt 哈希，并把该用户所有 `user_token.revoked` 置 true
（旧设备手里的刷新令牌立刻失效）。新密码只在弹窗里显示一次。

⚠️ 两点必须跟客服说清楚：

1. **旧 access token 最多还能用 2 小时** —— 平台端 JWT 无状态，没给单条 access
   做黑名单。所以「号被别人拿走了」的场景，重置密码之后对方 2 小时内还能动数据。
2. **游客（`is_guest`）重置不了**，后台会直接拒绝并提示原因：他连手机号都没有，
   设了密码也没法登录。正确做法是让用户先在 App 里点「保存进度」绑手机号。

短信通道接上之后还剩一件事：给 `mobile_verified = false` 的账号补一次验证
（重调一次 `/auth/bind-mobile` 带上码就翻成 `true`），这样后台一眼能看出哪些号
的号码是「用户自己填的、没验过」。

★ 为什么这条必须在 **HTTP 层**验：`code` 从 `required` 改成 `omitempty`
是 gin 的 binding tag，服务层单测**绕过**了它 —— 只有打真接口才看得见。
改坏了的表现是「点保存进度，提示参数错误」，一点线索都没有。

### 7.8.12 ★★ 号码已经被占用：不能只甩一行红字

游客绑定**最常见**的失败不是网络，是这个号码上**已经有一个账号**了 ——
家长以前在别的手机上玩过。原来界面上只有一行服务端文案「该手机号已注册」，
是个死胡同：

- 绑不上 ⇒ 这台手机上攒的东西永远存不下来；
- 那个号码上原本的账号也进不去（界面上没有任何入口指向它）。

现在按服务端码 `10010202`（`MOBILE_ALREADY_REG`）改口：说清「用它可以登回来，
但这台手机上刚攒的进度**不会**跟过去（还留在现在这个临时账号里）」，
并给一个按钮，把号码带进登录面板（预填，不用再打一遍）。

**为什么不做「合并账号」**：用户明确说了先放着。合并要先定「两个账号谁赢」
（积分取大？相加？农场存档用哪份？），那是另一个量级的问题。这里只保证
两件事：**不骗人**、**有出路**。

三条容易做错的细节：

| 细节 | 做错的样子 |
| --- | --- |
| 判 `errorCode` 而不是文案 | 拿中文 `includes('已注册')` 判断 ⇒ i18n 改一次文案就**静默失效**，退化成一行红字 |
| 按钮上的号码 = **上次提交**的号码 | 用输入框当前值 ⇒ 用户改号之后按钮跟着变，「用 139… 登录」而那个号根本没被占 |
| 开关面板时清 `error` / `errorCode` | 上一次的红字留到下一次打开 ⇒「刚打开就说这个号码已经有账号了」，用户什么都还没做；而且 `error` 是全 store 共用的，会跟着跑进登录面板 |

★ **`_probe-guest-entry.mjs` 的 [5] 是唯一能证明这个常量对得上的地方**。
单测里那个码是我们自己 `new ApiError(MOBILE_ALREADY_REG, …)` 塞进去的 ——
常量写成别的数字，单测照样全绿，线上却退化成「一行红字、没有出路」，
正好是这次要修的那个死胡同。[5] 自己用 `/auth/register` 造一个号来当
「已被占用」，而且**必须排在「真的绑一次」前面** —— 绑成功之后账号就不是
游客了，保存进度面板再也没有入口（设置页那个胶囊会变回纯文字）。

★★ 这一段踩过一个**很费时间**的坑，记下来：想用「新开 browser context」
拿一个全新设备，结果**家长向导**（`SetupWizard`，`fixed inset-0 z-[60]`）
自动弹了出来，而底部弹层只有 `z-50` ⇒ 面板看得见、点不到。`page.click`
点到的是向导底部那个「开始设置」大按钮上，面板一直停着，20 秒后超时，
**看起来像「改口那一块没渲染」**。教训两条：

1. 整屏层叠顺序：`z-[60]`（向导 / 导览 / 商店加载层）压得住 `z-50` 的
   BottomSheet。凡是「弹层里点不动」的怪现象，先看 `document.elementsFromPoint`
   打出来的整个栈，别猜。
2. 「点得到」只能用 `elementFromPoint` 判：`el.click()` 不走命中测试，
   被整屏层盖住也照样「成功」。所以 [5] 里加了一条
   「提交按钮真的点得到」的断言 —— 它当场把这个坑抓了出来（失败信息里带着
   实际命中的元素），而不是让人对着 20 秒超时发呆。

### 7.8.13 ★★ 首启连不上：停在一屏「重试」上，别放进空界面

§7.8.9 修的是**横条上的重试**（中途断网，界面已经打开、有数据可看）。
但首启是另一种情况：**一个令牌都没有**，`refresh()` 直接返回 `no-session`，
一条都不拉 —— 放进去就是一整套空界面（没任务、没积分、农场空的）。

横条那种「说清楚但不拦」的口径在**中途**是对的（要看一眼昨天的任务），
在**首启**是错的：这时候没有任何东西可看，空界面本身就是一句假话
（孩子会以为这个 App 是空的）。所以分两种：

| 时刻 | 处理 |
| --- | --- |
| 首启 / 账号没建成（`ready` 还是 false） | **整屏拦住**：`BootRetryPage`，一句话 + 一个「重试」 |
| 中途（界面已经在跑，`ready` 已是 true） | 照旧：`SyncBanner` 横条 + 重试，不拦任何东西 |

两处判定用的是同一个 `bootAccount === 'failed'`，靠 `ready` 区分先后 ——
这也是为什么启动 effect 里**必须**在 `ensureGuest()` 失败时 `return`，
不能接着 `boot()`：`boot()` 末尾无条件 `set({ ready: true })`，一旦跑了，
`!ready` 这个条件就永远不成立，那一屏也就永远不会出现。

`scripts/_probe-boot-retry.mjs` 守这条（9 条）：用请求拦截把 `/api/` 全
abort 掉造「连不上」，然后

1. 断言出现这一屏（不是空界面、也不是一直转圈的开场页）；
2. **把拦截关掉再点「重试」**，断言真的进了主界面 —— 拦住本身也是风险，
   写错就是永远停在启动页，所以「不是死路」这一半必须一起验。

⚠️ 判据只能看 DOM（`[data-boot-retry]`），不能看「转圈没了」：
开场页和这一屏都是整屏替换，`innerText` 那种模糊判据分不出它们。

#### 同一个坑的第二面：`boot()` 自己抛错

`boot()` 原来**没有 try/catch**。三个 await（`seedIfEmpty` / `loadSettings` /
`refresh`）里任何一处抛错，`set({ ready: true })` 就永远执行不到 ——
**永远停在开场页转圈**：没有报错、没有重试、没有出口，用户只能卸载重装
（数据全丢）。而 `refresh()` 自己也没有 try/catch，链路上任何一步
（Dexie 写不进去、服务端返回的形状不对导致的 TypeError）都会一路冒上来。

现在 `boot()` 收口成 `try / catch / finally`：

| 步骤 | 结果 |
| --- | --- |
| 成功 | `ready: true`，`bootError: null` |
| 抛错 | `bootError = e.message`，**`ready` 保持 false** |
| 无论如何 | `loading: false`（否则骨架/按钮永远转） |

界面用同一个 `BootRetryPage`（标题/正文/提示可覆盖）接住：
「启动时出了点问题」+ 错误原文 + 「再试一次看看。要是还不行，把这一屏
截图发给我们。」—— 提示语**不能**照抄网络那版（「网络好了点重试」），
这时的原因多半和网络无关。

⚠️ 两处的判据都是 `!ready`，靠 `bootAccount === 'failed'` 和 `bootError`
区分是「没账号」还是「启动炸了」。别把这两条并成一个 `if`：账号那条要
先跑（没账号时 `boot()` 压根不该跑，也就不会有 `bootError`）。

### 7.8.14 ★★ 绑完之后没人收尾：一句承诺没人兑现

`reason === 'coupon'` 那一支的面板上写着「绑完就能继续」。但事实是：
**花券那次请求已经失败了**（服务端回 `10010802`，一个字节都没动），
绑定只是给账号补了个手机号，`bindMobile` 成功后把面板一关就结束了。

于是人看到的是原来那一屏：东西还在，横条没了，**什么都没发生**。
他不会知道刚才那一步没生效，也不会知道该再点一次 —— 那句「绑完就能继续」
是句空话。这类问题不会报错，只会表现为「孩子说点了没反应」。

现在绑成功之后按**当初为什么弹**给一句不同的收尾：

| 原因 | 收尾 |
| --- | --- |
| `coupon` | 「账号存好了」/「刚才那一步没生效 —— 回到刚才那一屏，再点一次就行。」 |
| `launch` / `manual` | 「进度存到账号里了」/「以后换手机、重装 App，用这个手机号和刚才设的密码就能登回来。」 |

两支都不能省：`coupon` 要交代「没生效 + 下一步」，其余那支要交代
**怎么回来**（密码是他刚设的，不说等于白设）。

★★ **为什么不做「自动重试刚才那一步」**：那条链路在 `api/client.ts` 里，
被拦时只有一个 `() => void` 的回调（`bindGuestBlocked`），**没有「刚才要做什么」
的上下文**。要做得对，得引入一个 pending action 队列，而兑换和心愿两条路径的
入参完全不同（商品 id + 数量 vs 心愿 id）。更要紧的是：自动重放一次**扣券**
动作，一旦重放逻辑写错就是**重复扣钱** —— 这个代价比「再点一次」高得多。
先把「说清楚 + 给下一步」做到位，别半吊子地自动重放。

★ 判据要断言**按原因分支**，不能只断言「有 toast」：把 `why === 'coupon'`
改掉之后，只有 `coupon` 那一条会红，其余（含「自己点保存进度」那条）
照样绿 —— 这正好证明分支是活的、而且两条都被测到了。
`绑失败时**不**发成功提示` 那条守的是反方向：失败还报成功，人会以为
进度存下来了，然后心安理得地卸载。

## 7.9 第四期：兑换商城上云（2026-11-02）

商品、兑换、兑现、下架全部走服务端。**兑换是服务端扣钱**，客户端那条
本地事务（扣券 + 扣分 + 写记录，见 `store/useApp.ts` 的 `redeem`）在在线
模式下**整条不走**。

### 7.9.1 `/redeem/list` 是**视图**，不是数据源

这是这一期最容易踩的一脚。那个接口返回的是 `RedeemRow`：

- 价格字段叫 `price`（本地叫 `cost`）；
- 带分账预览 `plan` / 够不够换 `can_redeem` / 今天还剩几次 `remaining_today`；
- **已经按「给孩子看」的口径滤过了**：已下架、一次性换过、缺货的行**不返回**；
- 而且它是**混排**的：`source === 'wish'` 的行是家长定过价的心愿商品。

拿它当镜像源，三件事会同时坏掉：

| 症状 | 原因 |
| --- | --- |
| 家长管理页里「一次性 · 已换过」的商品**凭空消失** | 被过滤掉了，而兑换记录还在 |
| 兑换页里同一件东西出现**两遍** | 心愿行被写进了兑换品表 |
| 「每天最多 N 次」变成「不限次数」 | `limit_per_day` 没带 |

所以服务端加了 `raw: true`：**一条都不删**，改为在每行上标 `visible`。
三条过滤规则在 `RedeemService.ListItems` 里**只写一处**，默认模式和 raw
模式共用 —— 不会出现「列表里没有它、兑换时又说能换」。

客户端拉商品**永远用 `raw: true` + `include_archived: true`**，见
`sync/pull.ts`。`visible` 落到 `RedeemItem.visible`，`loadRedeemItems()`
按 `visible !== false` 过滤（本地版不写这个字段 ⇒ `undefined !== false` 恒真，
行为不变）。

### 7.9.2 商品的 id **不加前缀**，记录的 id 要加

服务端建商品时用的是**客户端给的 id**（`/redeem/item/create` 的 `id`
→ `redeem_item.item_id`），两边本来就是同一个字符串，所以：
`RedeemItem.id` 在本地和服务端**完全一致**，写接口不用做任何 id 翻译。

兑换**记录**不一样：服务端生成 `RR…`，本地生成 `rr…`。所以加 `srv_rr_`
前缀，`online/redeem.ts` 的 `serverRecordId()` 负责剥 —— 剥错了不报错，
只会收到「兑换记录不存在」，而界面显示的是「记录没了」。

> 顺带一条：在线版的 `redeemItems` 表在拉取时**整张清空**（不是只清 `srv_`
> 行）。理由和别的表不同 —— 这张表的 id 没有前缀，没法从 id 上分辨来源；
> 而在线版里它**只可能**有云端数据（`seedIfEmpty` 在在线模式一个字节都不写，
> 写接口全是写穿）。

### 7.9.3 已取消的记录**不许**拉进来

`cancelled = true` 的兑换是**退过款**的，那笔兑换在事实上没有发生。拉进来：

- 家长管理页会多出一条「待兑现」（`!fulfilled`）—— 东西早退了，家长却以为
  还欠孩子一次；
- `redeemedToday` 会把它算进「今天换过几次」，孩子明明没换成却被限流。

服务端三个判据（`HasRedeemedOnce` / `CountTodayByItem` / `CountRedeemedByItem`）
全都带 `cancelled = false`，所以丢掉它们和「一次性换过」的判断是**一致**的。

### 7.9.4 `updateBody` 的判据是「键在不在」，不是「值是不是 undefined」

编辑器的 patch 永远是整份（`{ name, emoji, category, cost, note, limitPerDay, once }`），
其中 `note` / `limitPerDay` 可能是 `undefined` —— 那是家长**清空**了它们。

按值判的话，这两个字段**永远清不掉**（备注删了还在、限额取消不掉），
而且不报错。所以 `online/redeem.ts` 里是「键在就发，值是 `undefined` 就发零值」
（`note → ''`、`limitPerDay → 0`、`stock → -1`），并有一张 `UNSET` 表兜底。

### 7.9.5 失败提示和本地版**一字不差**

`redeemFailToast()` 把服务端的业务码翻成孩子看得懂的话（余额不足 / 只能换一次 /
今天换太多了 / 换光了 / 下架了）。不翻的话孩子会看到「这次兑换没成功 — 余额不足」，
而本地版写的是「兑换券和积分不够啦 · 再攒一攒吧」—— 同一件事两种说法，
孩子会以为是两件事。

### 7.9.6 「今天换过几次」两边日界不同 ⇒ 在线版采信服务端的数

`redeemedToday` 在**本地版**用 `settings.dayStartHour`（默认凌晨 4 点）算「今天」，
服务端 `RedeemService.todayStart` 按**自然日 0 点**算。两个日界在
**00:00–04:00** 这四小时里差一天：

| 时间 | 服务端的「今天」 | 本地的「今天」（逻辑日） |
| --- | --- | --- |
| 11-03 01:00 | [11-03 00:00, …) | [11-02 04:00, 11-03 04:00) |

于是 11-02 23:00 换的那一次：服务端算「昨天」，本地算「今天」。

⚠️ **方向是「界面更严」，不是更松**（这一节原来写反了，2026-11-02 晚改）。
本地会把「昨晚那次」多算进来 ⇒ `maxed` 为真 ⇒ **按钮被禁掉**，
而服务端明明会放行。孩子看到的是「每天最多 1 次 · 今天用完了」，
实际还能换 —— 按钮坏了和「被无故拒绝」对孩子是一回事。
反方向（界面放行、服务端拒绝）不会发生：`limitPerDay` 的闸门在服务端，
它不看界面说什么。

⇒ 在线版**采信服务端给的 `today_count`**（`/redeem/list` 每行都带，
和 `visible` 同一个口径：服务端算好，界面不自己再推一遍）。
拿不到（没拉到 / 离线）才退回本地那份 —— 显示 0 会让限额在离线时形同不存在。
规则本身抽成了纯函数 `pickTodayCount`（`src/domain/redeem.ts`），
因为 `isOnlineMode` 是构建期常量、`vitest.config.ts` 钉成 `local`，
在 store 里根本造不出「在线版」来测。

要彻底对齐（连本地版也按 0 点算），得让服务端按家长设的日切点算 ——
那是「把家长设置也上云」之后的事（见 §7.4 的边界）。

### 7.9.7 验收

```bash
npm run lint && npx vitest run && npm run build
node scripts/_probe-redeem-online.mjs      # 32 条，真连后端
```

探针验的是**界面状态 == 服务端状态**，不写死「点完显示 X」：商品在不在服务端、
扣的钱是不是标价、本地流水是不是全是 `srv_ledger_`（没被记两遍）、
一次性商品在孩子那一页消失但家长管理页还在、下架翻的是服务端的标志位、
断网时一个字都不落本地、**「今天换过几次」界面 == 服务端 `today_count`**。

⚠️ 探针复现不了 00:00–04:00 那个窗口（没有改时钟的口子，除非真在凌晨跑），
所以那一步守的是**不变量**；窗口本身的判据在 `redeem.test.ts` 的 `pickTodayCount`。

⚠️ 它每跑一次**真的花掉 2 件商品的钱**（兑换是真扣款）。所以探针商品定价
`COST = 1`，跑几十次才需要给测试账号补币。

## 7.10 顺手修掉的一个静默 bug：分页参数叫 `pageSize`（2026-11-02）

做兑换这一期时被 `_probe-write-through.mjs` 抓住的，**不是**兑换引入的，
而是它把账号流水推过了 30 条，把一个一直存在的坑照出来了。

### 症状

`本地余额 12 / 服务端 136`。界面上没有任何异常，只有那一条断言红。

### 原因

服务端**两种分页 DTO 并存**：

| 出处 | json 标签 |
| --- | --- |
| `entities.Paginator`（钱包流水 / 兑换记录 / 心愿…） | **`pageSize`** |
| 手写的那几个（`/task/pending-review`） | `page_size` |

客户端三处全写成了 `page_size`。传错的不会报错 —— `ShouldBindJSON` 的返回值
被 `_ =` 丢掉，`PageSize` 留在 0，服务端 `Normalize()` 兜底成 **30**。

于是 `walletLedger(1, 200)` 永远只拿到 30 条。而本地 `balance` 是
**流水求和**（`currentBalance`）⇒ 账号攒到第 31 条之后，余额就开始少，
少掉的正好是最早那些大额入账（第一页之外的）。

### 改法（两层，缺一不可）

1. `api/wallet.ts` / `api/redeem.ts` 改发 `pageSize`；
2. `sync/pull.ts` 里 `pullLedger()` / `pullRedeemRecords()` **翻页拉全**
   （每页 200，`list.length < 200` 停，保险丝 10 页）。
   只改参数名的话，流水超过 200 条的账号照样会少。

### 顺带补上的一条规矩

「先清后写」的表现在**只在拉取成功时才动**（判据是 `ledger !== null`，
不是「数组空不空」）。原来流水接口一失败，本地账本照样被清空、再写 0 条 ——
余额当场归零，而界面上只是「今天没加分」。

## 7.11 第五期：心愿商场上云（2026-11-02）

六个动作全部写穿：家长定价、孩子许愿、孩子兑换、家长确认、家长收尾、家长回绝。
本地那套 `db.transaction(...)` 在在线模式下**整段跳过** ——
扣券 / 扣积分 / 开盲盒 / 授予游戏全在服务端一个事务里。

### 7.11.1 商品目录**不在服务端**，服务端只有一份副本

`wish_item` 表是 `games/wishCatalog.ts` 常量在库里的**副本**（`seed/wish_catalog.go`
每次非生产启动都会 upsert 一遍）。界面渲染读的仍是常量 ——
和 `RedeemItem` 相反（那张表的真相是服务端，因为家长会自己建）。

**两条目录并存的前提是 id 完全一致**：

| 本地常量 | 服务端种子 |
| --- | --- |
| `WISH_BLINDBOX_ID = 'wish-blindbox'` | `seed.WishBlindBoxID` |
| `wish-game-${s.id}` | `"wish-game-" + g.GameID` |
| `wish-popmart` / `wish-dino` / … | `seed.PhysicalWishes` |

改一处忘另一处 ⇒ 界面上一件商品点进去「没有这件商品」（`10070101`）。

⚠️ **`/wish/list` 不能当「商品全集」**：它会把 `gamebox` 且**已拥有**的商品
直接滤掉（换不了、也没动作）。拿它当数据源会得出「家里没有这款游戏」的错误结论。
拉取时只用它取 `open` + `voucher_price`，见 `mapWishOffer`。

### 7.11.2 定价在本地是「一个布尔」，不是一张表

服务端**不返回** `opened_at` / `closed_at`，只给一个算好的 `open`。
而本地读 `WishOffer` 的每一处（`wishesAwaitingReply` / `wishShelf` /
`wishExpress` / `wishRedeem`）判的都是「**没有 `closedAt`** 且价 > 0」。

所以 `mapWishOffer` 的规则是：

- `open && voucher_price > 0` → 写一行，**不带 `closedAt`**；
- 其余（没定过价 / 定过又关了）→ **不写行**。

两种「不写」在界面上是同一个结果：现在不能换，心愿单里那条重新变回「等爸妈回应」。

⚠️ **不能**写成「有行但 `closedAt: 0`」—— 那样家长关掉的东西孩子还能换。
这条在探针里有一条专门的断言（第 6 步）。

### 7.11.3 已取消的订单**要**留下（和兑换记录相反）

兑换记录里 `cancelled` 直接丢（§7.9.3），因为那笔兑换在事实上没发生。
心愿单**相反**，`cancelled` 必须留着：

- 它是孩子能看见的一段历史（「爸妈这次先不换」+ 原因）；
- `WishItemView.lastRejectReason`（「上次爸妈说：…」）就是从最近一条取消单读的
  —— 丢掉的话孩子刚被回绝，卡片上却没有一句解释。

不会因此把退掉的游戏当成「已拥有」：`redeemedGameIdsFrom` 已经显式排除了
`cancelled`。

### 7.11.4 服务端那道「实物必须有收货信息」改成了可选

**症状**：所有实物心愿永远换不了。孩子点兑换 → `10071201`，
而客户端**没有任何地方能填地址**（spec §9 的家长表单是 P3，一直没做）。
本地版没有这道闸，同一个动作在那边是通的 —— 两个版本的差别不该是
「这个功能在服务器版坏掉」。

**改法**（`wish_srv.go` 的 `Redeem`）：收到 `ship` 就存（`purge_after` 90 天），
没收到就留空，只打一条 info 日志。「券真扣」这条底线不受影响。

**那个洞已经补上了（2026-11-02 晚）**：`/wish/done` 的 `WishHandleReq` 现在认 `ship`，
家长在「确认兑换」那一屏就能填地址 —— 这是地址的**唯一入口**，
兑换那一刻孩子那头没有表单（spec §9 的家长表单还是 P3）。

三个细节值得记：

- **地址为空时一个字都不写**（`shipColumn` 返回 `false`）。家长只点「已经买好了」、
  没填地址，不能把兑换时存过的地址覆盖成空。
- **过期时间由服务端算**（90 天）。客户端的 `ShipDraft` 类型里**没有** `purgeAfter`，
  想编也编不出来（编了也只会被覆盖，而且两边时钟不保证一致）。
- **校验必须在客户端**（`domain/wishShip.ts` 的 `shipFormIssue`）：服务端对空地址
  是静默不存、不报错。家长填了一半提交，界面照样「已经完成啦」，地址其实没落库 ——
  等发货那天才发现，而那时候孩子已经以为买好了。

#### 一个必须记的坑：`serializer:json` 对 **map 更新**不生效

第一版把结构体直接塞进 `fields["ship"]`，`/wish/done` 直接 500：

```
sql: converting argument $2 type: unsupported type entities.WishShipInfo, a struct
```

`ship` 这一列在模型上写的是 `gorm:"column:ship;type:text;serializer:json"`，
但 `UpdateOrderCAS` 是 **map 更新** —— serializer 只作用于**模型字段**，
map 里的值被原样丢给数据库驱动。所以 map 更新这一列必须自己 `json.Marshal` 成字符串；
读的时候 serializer 照样反序列化回来，两边是通的。
（`Redeem` 里那段老代码有一模一样的毛病，只是从来没有客户端送过 `ship`，
所以从 2026-11-01 写下来一直没暴露。）

### 7.11.5 装包失败要**回头调服务端的取消**

服务端只做「授予游戏」（写 `user_game`），插件包在本机 `gameKv` 里，它管不到。
所以游戏类心愿是唯一一个「服务端成功之后客户端还要再做一步」的动作：

```
/wish/redeem  → 扣钱 + 授予游戏 + committed（服务端事务）
      ↓
installLocalGame(gameId)
      ↓ 失败
/wish/cancel  → 退两种币 + RevokeGame（服务端事务）
```

**不要**在客户端自己造一笔退款账 —— 那会变成「本地退一次、服务端那单还挂着」，
两边永远对不上，而且不报错。

取消成功后本地还要 `detachGameKv`（只摘安装，**保留存档**）：
撤销的是这笔交易，不是孩子玩出来的进度。

### 7.11.6 订单 id 要加前缀 —— 它和本地 id **只差大小写**

服务端 `WO1793609808…`，本地 `woabc123`。肉眼分不出，
不加前缀的话本地那行会被当成服务端订单发给 `/wish/cancel`，
回来的「订单不存在」在界面上显示成「这单没了」，而本地那条其实好好的。

⇒ `SRV_WISH_ORDER_PREFIX = 'srv_wo_'`，`serverWishOrderId()` 剥前缀，

## 7.12 第六期：游戏币 + 插件扣积分上云（2026-11-02）

### 7.12.1 币的余额在本地是「算出来的」，上云之后要怎么办

本地版的契约是「**余额 = 账本 delta 之和**」（`gameCoinBalanceOf`），
从来不存 `balance` 字段 —— 理由和宿主那三套币一字不差：存一份就会出现
「余额和流水对不上」，而且**不报错**。

上云之后这条契约原封不动，但账本的**内容**换了个来源：

| | 本地版 | 在线版 |
| --- | --- | --- |
| `__coin` 是什么 | 逐笔账本（`+5` / `-1` / `-1` …） | **服务端余额的镜像**（单行，`delta` = 余额） |
| 谁写它 | `addGameCoin` / `spendGameCoin` … | 拉取（`/game/coin/list`）+ 每次写穿成功后用**服务端返回的 `balance`** 覆盖 |
| 求和结果 | 余额 | 余额（一行，恒等于服务端） |

**为什么不做成「在线时直接问服务端」**：`host.gameCoinBalance()` 是插件
**每帧都可能调**的方法（画「还剩几个币」）。改成每次发一个 HTTP 请求，
一个 60fps 的小游戏能把接口打成筛子，而且没网时每帧都要等一次超时。
读 Dexie 是微秒级的。

**为什么敢把账本压成一行**：本地读币的地方只有 `gameCoinBalanceOf`（求和）
和调试桥的 `gameCoins`（也是求和），**没有任何界面显示币的流水**。
明细在服务端的 `game_coin_ledger` 里，要看就去 `/game/coin/ledger`，
别在本地重建一份。

> ⚠️ 千万别在在线模式下再往这个数组里 `push` —— 那会变成
> 「服务端余额 + 本地增量」，两边各自演进，而且不报错。

### 7.12.2 拉取要**整表清掉再写**（`/game/coin/list` 只返回开过钱包的）

服务端不写空行：没开过钱包的游戏**不在返回里**。
所以「只覆盖返回的那些」会留下一个静默 bug —— 某款游戏在服务端被清零 /
钱包行没了，本地镜像还留着旧数字，孩子看到的币比服务端多。

⇒ `clearGameCoinMirrors()` 扫 `gameKv` 里所有 `:<__coin>` 键删掉，再写。
只在 `/game/coin/list` **拉成功**时做（`null` = 不知道，别清 —— 清了等于
把孩子兜里的币拿走）。

`gameKv` 也进了那个「先清后写」的 `db.transaction`，所以要么全成、要么全不成。

### 7.12.3 六扇门改走服务端，但**返回值契约一个字都不能变**

插件是按本地版那份契约写的：`spendGameCoin` / `buyGameCoin` 返回 `boolean`
（不够 = `false`，**从不抛**），`redeemGameCoin` / `mintVoucher` 返回
`Promise<number>`（不开放 = `0`），`mintGameCoin` 返回 `void`。

所以 `hostApi.ts` 里每扇门只多一行 `if (isOnlineMode)`，语义翻译放在
`online/coin.ts`：

| 服务端 | 翻成 |
| --- | --- |
| `10040901` 游戏币不足 | `false` / `0` |
| `10020301` 积分不足 | `false` |
| 断网 / 401 / 5xx | **弹一条提示 + 返回 `false`**（`guarded()`） |

最后一行是有意的：**断网策略是「直接不可用 + 明确告诉用户要联网」**，
所以既不装作成功（那等于静默丢数据），也不把 `ApiError` 抛给插件
（插件没写 catch，症状是「点了没反应」，而真因谁也看不到）。

### 7.12.4 三个「本地有守卫、服务端没有」的地方

在线版里守卫必须在**两边各站一份**，否则服务端会把本地那个「不」变成「行」：

1. **数量 ≤ 0 不发请求。**
   本地 `addGameCoin` 对 `n <= 0` 是**静默不写**（币只进不出）；
   服务端 `binding:"min=1"` 会报参数错误 —— 那会让插件的
   「这一局没赚到币」变成一个异常。`oMintCoins` 在发请求前就挡掉。
2. **买币的单价必须传，且必须 > 0。**
   服务端 `points_per_coin` 是 `omitempty,min=1`，**不传就兜底 10**。
   传 0 会被静默当成 10 ⇒ 一局 1 分的游戏变成一局 10 分。`oBuyCoins` 挡掉。
3. **`voucherPerCoin = 0`（manifest 说不开放兑换）一个请求都不发。**
   服务端读不到 manifest，也不接受客户端传汇率（那等于把印钞机的旋钮交出去），
   它**照换不误** —— 发了就等于绕开家长的那个开关。

### 7.12.5 一个已知的汇率不一致（有兜底）

本地按 manifest 的 `economy.voucherPerCoin` 算（可以是 2、3…），
服务端**写死 1:1**（`game_coin_srv.go` 里 `rate := int64(1)`）。

当前发布的插件全是 1（`cloudfarm` 是 0 = 不开放），所以现在对得上。
`oRedeemCoins` 仍然**以服务端返回的 `vouchers` 为准**，并在
`manifest 算出来的 != 服务端发的` 时 `console.warn` 一条
「汇率不一致」—— 让下一个人一眼看到根因，而不是去猜「券怎么少了」。

### 7.12.6 顺手修掉的一个静默 bug：幂等键变成常量

服务端拼幂等键原本是 `"game_coin_spend:" + req.ClientRequestID`。
客户端**不传** `request_id` 时拼出来是 `"game_coin_spend:"` —— 一个**常量**，
于是第二次调用撞上账本唯一索引，被翻成「该笔记录已存在」（610）。

症状是「第一次能玩，第二次开始一直说已经做过了」，而且**只发生在
不传 `request_id` 的客户端身上** —— 带 id 的客户端永远看不到。

⇒ 服务端加了 `idemKey(prefix, reqID)`：`reqID == ""` 时返回空串，
让账本落 `NULL`。五处调用点（buy 两条、spend、redeem 两条）+ `MintVoucher`
一起改了。客户端这边每次调用也都给一个新键（`newCoinRequestId()`）。

### 7.12.7 验收

```bash
npm run lint && npx vitest run && npm run build
node scripts/_probe-coin-online.mjs          # 44 条，真连后端
```

探针**不点界面**，而是装一个 `data:` URL 的**合成插件包**，让它的
`mount(container, host)` 把宿主给它的那个 `host` 挂到 `window.__probeHosts`，
然后调 `buyGameCoin` / `spendGameCoin` / `mintGameCoin` / `redeemGameCoin` /
`mintVoucher` / `spendPoints`。

为什么绕这一下：这样调的是**插件真正拿到的那份 `HostApi`**
（`mountGame` → `pluginHostApi` → `makeHostApi`），而不是给探针另开一扇门 ——
另开一扇门验的就不是生产链路了。

断言的是**界面状态 == 服务端状态**，每一条改数之后都重新查一次服务端：

- 买币扣 `count × 单价` 分、币 `+N`、**本地镜像 == 服务端余额**；
- 玩一局币 `-1`；币不够返回 `false` 且服务端一分不动；
- 铸币 `+3`；`0` / 负数**一个字节都不写**；
- 换券：币 `-2`、券 `+2`、返回 `2`；
- manifest 汇率 0 时返回 `0`、服务端币和券都没变（那条「不发请求」的守卫）；
- 插件扣积分：服务端 `-3`、本地积分 == 服务端、本地流水全是 `srv_ledger_`、
  服务端那笔记成 `game_spend` + `ref_id = 游戏 id`；
- 发券：券 `+2` 且**币余额没动**（奖品直接发券，不经过币）；
- 断网：`spendGameCoin` / `spendPoints` 都返回 `false`，弹出「没发出去」，
  服务端币和积分**一分没动**；
- 重载后本地读数仍 == 服务端（说明是拉回来的，不是内存残值）。

⚠️ 两个细节：

- 探针**真花钱**（每跑一次 13 积分），所以单价都取得很小；
- 「装没装」的判据是 `kv(id)` 里有没有 `__bundle`，**不是** `kvOwnerIds()`
  里有没有这个 id —— `uninstall` 之后 `refresh()` 会再拉一次
  `/game/coin/list`，`${id}:__coin` 那行镜像又回来了（它是服务端钱包的缓存，
  不是安装残留）。拿 `kvOwnerIds` 判会恒红。

## 7.13 第七期：插件存档上云（2026-11-02）

插件存档是最后一块。它的形状和前面几期一样（读 Dexie、写服务端），
但**踩到的坑最多**，而且每一个都不报错。

### 7.13.1 形状

```
拉取  pullGameKv(gameId)   /game/kv/list 一次拿全（data + versions）
读    storage.get / list   读 Dexie（拉取刚搬进来，不再现问服务端）
写    storage.set          先 /game/kv/set（带 expected_version），成功才写 Dexie
卸载  uninstallGame        先删云端，删不掉就**不清本地**
```

**为什么 `get` 不现问服务端**：插件启动时会连着 `get` 好几个键（存档、设置、进度）。
每个都发一次请求，慢网下的开局就是好几秒白屏；而拉取刚刚才把整份存档搬进来
（`kv/list` 一次拿全），本地这份就是最新的。所以只有 `set` 走网络。

**为什么 `set` 失败要抛**（而不像游戏币那几扇门返回 `false`）：
`storage.set` 的契约本来就是 `Promise<void>`，本地版也可能 reject；
而「存档没存上却装作存上了」是这个 App 最不能接受的失败方式。
抛之前先弹一条提示（5 秒节流，否则插件每次操作都 `set` 一次会糊满屏幕）。

### 7.13.2 三个坑，都不报错

#### ① 软删的尸体把 upsert 吞了 —— **写成功，但谁也读不出来**

服务端 `BaseModel` 带 `gorm.DeletedAt`，GORM 的 `Delete` 默认是**软删**；
而 `Get` / `List` 都会自动追加 `deleted_at IS NULL`。

于是：卸载游戏（软删全部键）→ 重装 → 插件第一次 `storage.set` 走**无锁 upsert**
（新设备没有版本号）→ 命中那条软删的行 → 只改 `value` / `version`，
`deleted_at` 原样留着 ⇒ 接口返回 200，版本号还往上走，客户端认为存上了，
而这一行**对所有读路径都不可见**（包括下一次拉取）。

症状：写成功、零报错、换台设备进度全丢。
实测是这样暴露的：探针里「服务端有了这个键」失败，而 SQLite 里明明躺着那一行。

两处一起修（缺一不可）：

- `Delete` / `DeleteGame` 改 `Unscoped()` **硬删** —— 「卸载」的语义就是数据没了，
  软删只会留下一条读不到、却仍占着唯一索引 `(uid, game_id, kv_key)` 的尸体；
- upsert 的 `DoUpdates` 里加 `"deleted_at": nil` —— 历史数据 / 后台标记仍可能
  留下软删的行，只要 upsert 不清它，那一行就永远写不进去。

> 顺带修掉同一处的一个哑巴 bug：`DoUpdates` 原来写的是
> `"updated_at": gorm.Expr("updated_at")` —— 把列赋给它自己，等于**永远不刷新**。
> upsert 走原生 clause，不经过 GORM 钩子，必须手写 `time.Now().Unix()`。

#### ② 新行落 `version: 0` ⇒ **前两次写完全没有冲突检测**

客户端把 `expected_version = 0` 当作「我手里没有令牌」的哨兵，服务端收到 0
就走无锁 upsert。如果新行落 0，客户端缓存到的也是 0 ⇒ 下一次写**又走无锁路径**。

结果：一个键的前两次写之间没有任何冲突检测，两台设备互盖一句话都不报。
修法是插入时 `if kv.Version < 1 { kv.Version = 1 }`（回档路径本来就这么传，对齐它）。
现在 `version: 0` 只有一个含义：**这一行不存在**。

#### ③ 同一个键并发 `set` ⇒ 必然 `10040701`

`set` 要带 `expected_version`。两个 `set` 并发出去，第二个带的还是旧版本。
所以同一个键的写排成一条链（`chains`，键是 `gameId\0key`）：

```ts
const next = prev.then(() => runSet(...), () => runSet(...))
```

第二个回调是给**前一个失败**用的 —— 只写 `prev.then(run)` 的话，一次失败会把
这条键的写链**永久卡死**（后面每次 `set` 都挂在 rejected 上）。

### 7.13.3 冲突时**以本机为准**

撞 `10040701` 时的处理不是「把本地覆盖成服务端的」，而是重读版本号再写一遍。
理由：孩子正在这台机器上玩，他刚做的那一步必须留住；对方那份是上一次玩的结果。

只重试**一次**。再撞说明两台设备在抢同一个键，重试也解决不了，就把冲突抛给上层
（提示「存档在别的设备上改过」）。重试时 `console.warn` 记一行原因 ——
否则「我明明存了」这种反馈无从查起。

### 7.13.4 卸载：先删云端，删不掉就别删本地

`deleteGameKvOnServer` 返回三种结果，因为调用方要做的决定不一样：

| 结果 | 含义 | 调用方怎么办 |
| --- | --- | --- |
| `ok` | 删了（或本来就没有） | 清本地 |
| `no-game` | 服务端不认识 / 没拥有这款游戏 | **当作删掉了**，清本地（它本来就没有云端存档） |
| `failed` | 网络 / 5xx | **不清本地**，弹提示 |

第三种是关键：否则「卸载」会变成「本地删了、云端还在」，重装就捡到上一次的存档
—— 本地版明确不允许这件事。

### 7.13.5 拉取放在大事务**外面**

`pull()` 里任务 / 账本 / 农场那些表是一个 Dexie 事务一起写的，
但插件存档**逐个游戏、在事务外、各自 try/catch**：

```ts
for (const g of await listInstalledBundles()) {
  try { kv.keys += (await pullGameKv(g.gameId)).written }
  catch { kv.failed++ }
}
```

原因：`/game/kv/*` 有 `checkGameExists` 这道闸（游戏要在目录里**且已拥有**），
本地预置 / 走查用的合成包会拿到 `10040401`。放进大事务里，一个没拥有的游戏
就能把任务和流水一起带崩。

`pullGameKv` 还有一条：**服务端版本比本地记着的旧就跳过**。
拉取和写穿会并发 —— `set` 刚打完服务端、正在写 Dexie 时，一次拉取可能带着
更早的快照回来，照写就把刚存的进度盖回去了，而且不报错。

### 7.13.6 所有权这道闸：三张表，一个真实缺口

`/game/kv/*` 的闸（`checkGameExists`）要三件事：**在目录里** + **没下架** +
**`default_owned = 1` 或 `user_game` 有行**。

服务端在**四个**真实路径都会写 `user_game`（默认拥有 / 购买 / 心愿 / 兑换码），
所以正常买、正常换、正常开心愿的玩家不会撞。会撞的只有一类：
**本地判定「拥有」但服务端没有那行** ——

| 情形 | 当时会不会撞 | 现在 | 说明 |
| --- | --- | --- | --- |
| 购买 / 兑换码 / 心愿换来 | 不会 | 不会 | 服务端四个 grant 点都写 `user_game` |
| `grantGame`（devtools 调试预置） | **会** | 不会（界面直接显示「未拥有」） | 只往**本地账本**记一笔，服务端不知道 |
| 恢复备份后本地装了包 | **会** | 不会（同上） | 包是本地恢复的，服务端没有购买记录 |
| 目录里 `default_owned = 1` 的 | 不会 | 不会 | 服务端直接免检所有权 |

当时的症状：**游戏能玩、界面也显示已拥有，就是存档存不上**（`10040401`）。

> ⚠️ 别把探针「借 `cloudfarm`」的理由写成「测试账号买过它」——
> 实测这个账号的 `user_game` 是**空的**。借它是因为目录里 21 款游戏
> **只有 `cloudfarm` 是 `default_owned = 1`**，服务端对它免检所有权。
> 随手编一个 id 才会被 `10040401` 拒掉。

客户端那边的「拥有」也不是一份：`ownedGameIds`（账本 + 默认拥有）、
`installedBundles`、`wishOrders.openedGameId` 三个来源，`wishOwnedSet` 取并集。
**它不是服务端那张表**，所以不能拿它当「服务端会不会放行」的判据。

## 7.14 第八期：存档还原点（2026-11-02）

> 服务端 `/api/game/snapshot/*` 早就写好了（自动快照、日切基线、
> 回档前先存一份、回档记录），但客户端**一行都没接**，界面上没有入口 ——
> 等于「孩子把存档玩坏了能一键退回」这件事，只有后台能手动做。
> 这一期只做一件事：把它接到家长能点到的地方。

### 7.14.1 快照是**按 key** 存的，家长要的是**一个时间点**

服务端一个 key 一份快照（`save` 一份、`bag` 一份、`settings` 一份）。
家长看不懂这个粒度 —— 他要的是「退回到昨天下午」。

所以 `src/online/snapshot.ts` 里有一层纯函数 `groupMoments(rows, gapSec = 3)`：
把相邻 **≤ 3 秒**的快照并成一个「还原点」，`at` 取这一组里**最新那条**
的 `created_at`（回档时直接把它传回去）。

★ 为什么不是「`created_at` 严格相等」
  快照是按 key 存的，而一个游戏常常在一两秒里连着写两个键（一局结束先写
  `save` 再写 `settings`），两条跨了秒就会裂成两组，界面上看着像「存了两次」。
  3 秒是「一次用户动作」的合理宽度。
  （这一条原来写的是「手动存点时循环调 `create`」—— 手动存点 2026-11-02 已去掉，
  见 §7.14.11；分组的必要性没变，只是来源从「循环」变成了「游戏自己连着写」。）

★ 同一组里同一个 key 可能有多条（几秒内连存两次），
  只认**最新那条**的 `size` —— 否则「大小」会按快照条数翻倍。

### 7.14.2 回档用 `restore-by-time`，不用逐个 `restore`

`restore` 一次只恢复一个 key，整个游戏要调 N 次：N 个请求，中途失败
就留下「一半旧一半新」的状态 —— 那种状态没有任何人想要。
`restore-by-time` 是**一次调用恢复整个游戏**（每个 key 各取该时刻之前最近的一份）。

⚠️ 服务端的判据是 `created_at <= at`（**含**边界），不是 `<`。
   写成 `<` 的话，「退回到我刚存的那个还原点」会退到它的**上一份**，
   而界面上显示的正是刚存的那份 —— 差一步，且不报错。

⚠️ **回档之后必须 `pullGameKv`**（`restoreToMoment` 里做的）。
   服务端已经把存档改回去了，本地 Dexie 还是新的那份 ⇒
   界面和下一次打开游戏看到的都是「没退回去」，而服务端其实退了。
   这种「两边不一样且不报错」是本项目最怕的形态。

### 7.14.3 三个「不报错」的坑（这一期全是这类）

#### ① 时间戳是 **Unix 秒**，`new Date(秒)` 会得到 1970 年

`created_at` / `at` 全程是秒（服务端 `time.Now().Unix()`）。
`momentLabel` 里少了 `* 1000`，界面上就变成
「已经退回到**1月22日 02:13**，重新打开游戏就是那时候的进度。」——
它看起来像「日期格式没写好」，实际是**单位错了**，而且不报错、单测也不会红
（没人断言过日期字符串）。

现在换算只在 `momentLabel` 里做一次，`Moment.at` / `RestoreLogRow.created_at`
全程保持服务端单位（回档要原样传回去）。`src/api/snapshot.ts` 头注释写明单位，
`snapshot.test.ts` 有一条专钉单位的断言（`momentLabel` 结果里不许出现「1月」）。

#### ② 用「列表多了一行」当判据是**错的**

探针第一版写的是「回档之后 `[data-snapshot-moment]` 至少多一行」，
结果红在 `1 行 → 1 行`：整条探针跑得比 3 秒还快，
回档产生的 `before_restore` / `restore` 快照和前面那几份**落进了同一组**，
行数一行没变 —— 看着像「列表没刷新」，其实列表刷得很对。

判据改成**原因标签**：界面必须显示出「回档前 / 回档后」。
（这类断言的通病：把「数据怎么组织」写进了断言，而组织方式是实现细节。）

#### ③ 服务端的审计备注会**漏到家长眼前**

回档时服务端给快照写一条 `note`：`从快照 #40 回档`（后台审计要那个 id）。
`Moment.note` 取的是这一组里第一条非空备注 ⇒ 界面上就出现
「从快照 #40 回档」，家长只会以为「要记住这个号」。

`isAutoNote()` 认这个形状并在界面上不显示它。
⚠️ 认不出来**不算错**（照常显示，顶多难看）；反过来「只显示白名单里的备注」
才是错的 —— 那样以后服务端或家长自己写了新备注，会静默一个字都不显示。

### 7.14.4 入口放在「游戏详情」里，而且只有在线版有

- **只有在线版**（父组件判 `isOnlineMode`）：本地版的历史版本根本不存在，
  摆一个空壳只会让人以为「功能坏了」。
- **放在详情页**，不放列表行：列表行一款游戏只留一个动作（装 / 卸 / 设为当前），
  这是 iOS 应用市场的口径。还原点是**低频 + 不可逆**的操作，
  不该躺在孩子每天滚的那一屏里。
- **回档只在这里做，而这里插件是卸载状态**（`PluginGameHost` 离开游戏页时
  就 unmount 了）⇒ 不存在「插件内存里还是旧状态」的问题。

界面（`features/settings/SnapshotSection.tsx`）：一段「系统怎么存的」说明
+ 还原点列表（时间 / 几个存档 / 大小 / 原因标签 / 「看看退回去会变成什么」/
「退回到这里」）+ 二次确认（「退回之前的进度会先存一份，所以还能再退回来」）
+ 底部「退回过」记录。锚点：`data-snapshot-section` / `-moment` / `-preview` /
`-preview-body` / `-diff` / `-restore` / `-confirm` / `-flash` / `-error` /
`-empty` / `-logs`。

⚠️ 这里原来还有一个「现在存一个还原点」按钮（`data-snapshot-save`），
2026-11-02 晚按家长的意思**去掉了** —— 理由见 §7.14.11。

### 7.14.8 后端顺手修掉：「保留策略」一直在假删

接界面的时候查了一次库，发现 `game_kv_snapshot` 的行数只增不减 ——
`/game/snapshot/list` 却一切正常（`cloudfarm` 的 58 行**全是软删的尸体**）。

原因：快照实体内嵌 `BaseModel`（有 `gorm.DeletedAt`），仓储里两处删除写的是
裸 `Delete` ⇒ GORM 翻译成 `UPDATE ... SET deleted_at = now()`，
`value`（整份存档，KB 级）原封不动留在表里。读取侧被 GORM 自动加了
`deleted_at IS NULL`，所以**行为完全正确、一条断言都不红**：

- 「每 key 保留 20 个」确实只返回 20 个 —— 只是**一个字节都没省**；
- 卸载后 `list` 是空的 —— 但行还在，`Unscoped()` 一查就全回来了。

两处都改成 `Unscoped().Delete(...)`（硬删）。快照是可再生的历史数据，
保留策略的意义就是释放空间 ⇒ 和 §7.13 对 `game_kv` 的结论一致。

回归断言断的是**物理行数**（`TestSnapshotRetentionFreesDisk` /
`TestUninstallDropsSnapshotRows`），去掉修复分别红在「还剩 30 行」「还有 2 行」。
探针也加了一条：卸载后 `/game/snapshot/list` 必须是 0（顺带证明 `Uninstall`
里那个 `SnapSrv != nil` 没走空分支 —— 走空分支只打一行 warning，接口照样 200）。

> 教训：**「删了」要看两种计数** —— 逻辑行数（读得出来吗）和物理行数（还占着吗）。
> 软删让这两者分叉，而所有基于「读」的断言只看得到前者。

### 7.14.13 还原点为什么会自己少（服务端加了总量配额）

上一节把「假删」修好之后，还有一层漏的：保留策略**只淘汰非基线快照**，
而日切基线（每天第一条）按设计永久保留。一天一条、按 key 累加 ⇒
一个孩子玩一年、一款游戏 5 个键就是 1825 行整份存档。

服务端本来就写着一个 `SnapshotMaxPerUser = 2000` 和错误码
`10041101 快照数量超出配额`，但**一个调用点都没有**（连客户端
`snapshotFailText` 都专门有一句「还原点太多了，等系统清理掉旧的再存」）。
原因是这个限额想做「超了就拒绝写入」，而自动快照挂在 `storage.set` 后面 ——
拒绝等于「存档写进去了、还原点没了」，调用方看不出区别。

现在改成**两级保留**（服务端 `enforceRetention`）：① 每键 20 个非基线（原有）；
② 单用户总量 ≤ 2000，超出就删最旧的（基线天然排在最前面，所以先被清的是它们）。

所以「日切基线永久保留」的准确含义是**「保留到总配额为止」**。
对界面的影响只有一条：**还原点会自己变少**，而且不会有任何提示 ——
这是刻意的，配额是省空间用的，不是账本。`10041101` 这个码因此删掉了
（结构上不可能被触发），客户端那句提示和对应单测一起删。

> 教训：一个「限额」如果只能靠**拒绝**来生效，而拒绝的那条路径又不能真的拒绝，
> 那这个限额等于没有。先想清楚「满了以后腾谁」，再决定要不要那个错误码。

### 7.14.9 「看看退回去会变成什么」（预览）

一排「今天 18:59 · 22 字节 · [回档后][回档前]」其实**没法判断该退哪一个** ——
家长真正要回答的是「退回去孩子会失去什么」。所以每行加了一个按需展开的预览：

```
save  第 1 版 · 22 字节
 · level：99 → 1
 · tag：“v99” → “v1”
 左边是现在，右边是退回去之后。只比最上面那几项，存档里的明细没展开。
```

**只比顶层字段**（`diffPreview`）。不递归的原因很实际：存档里一个 `plots`
数组就有几十项，逐项 diff 出来几百行，家长一个字都不会看。顶层那几行
（积分 / 天数 / 关卡）才是他判断的依据。

四类写法，每类都有单测钉着：

| 情况 | 写出来 |
| --- | --- |
| 两边都是标量 | `level：99 → 1` |
| 两边都是数组 | `plots：12 项 → 9 项`（长度相同就说「内容不一样（都是 3 项）」） |
| 现在没有、退回去有 | `coins：会补回来（20）` ← **措辞不能写成「会丢」** |
| 现在有、退回去没有 | `coins：会被删掉（现在是 20）` |

超过 4 条就截断，末尾写「还有 N 处不一样」。

#### 三个坑

**① 按需取，不要在列表里全拉下来。**
60 份快照 × 每份几十 KB = 几 MB，只为了一次点击。`previewMoment` 只在
「点开某一个」时调：每个 key 一次 `snapshotGet`（通常 1~3 个）+ 一次
`gameKvList` 拿「现在」。

**② 单个 key 被保留策略淘汰，不能让整块炸掉。**
那个 key 记一行「这个还原点已经被清理掉了」，其余照常显示。家长点开是想看
东西的，不是想看一句「操作没成功」。

**③ 这个键现在服务端上没有（卸载过）≠ 值是 undefined。**
直接 `diffPreview(undefined, value)` 会退化成「整份存档都不一样」——
信息量最少的那句话。正确做法：对象按空对象比（逐字段说「会补回来」），
数组/标量直接写「会补回来（1 项）」。

#### 顺手去掉的一处重复

手动存点原来带 `note: '手动'`，而 `reason` 已经是 `manual`（界面上那颗
「手动」标签就是它）⇒ 截图里出现「[手动][自动][当天起点] 手动」。
备注留给「家长真的自己写一句」，现在不传了。

### 7.14.10 真包验到哪一步为止（以及为什么探针还是合成包）

试过用**真正的云边小农场**跑这条链路，结论分两半：

**能做的**（真包在无头 Chrome 里跑得起来）：

- `installLocalGame('cloudfarm')` → v1.1.4 装上；
- `mountInto` → 真渲染出来了（WebGL 用 `--use-angle=swiftshader`），
  `canvas: 1`，0 个页面错误；
- 能点：`进入农场` → 教学卡（**吃首按**，要点「知道了」）→ 点地块 → 种子商店。

**做不了的**：**它不会自动存档。**
真包的存档只挂在它自己的状态变化事件上：

```js
C.on((e) => { if (e.type === 'change') { N(); ... } })   // N() → backend.set('save', ...)
```

脚本点「进入农场 / 知道了 / 选种子」都不触发 `save`，`/game/kv/list` 一直是空的，
控制台也**没有** `autosave rejected` —— 说明不是存档失败，是根本没存。
要真触发得走完整种地流程（选种 → 种下 → 等成熟 → 收），而无头环境里时钟慢，
一步要等十几秒，还不稳定。

所以探针取了个折中：**真键名 + 真体量，合成值**。

- 键名 `save` / `settings` 是从 `public/games/cloudfarm/cloudfarm.plugin.mjs`
  里读出来的（`backend.set("save", ...)` / `backend.set("settings", ...)`），不是编的；
- `settings` 写到 **1734 字节**，带 12 块地的 `plots` 数组 —— 真存档就是这个量级；
- 走的是**真宿主链路**（`host.storage.set` → `/game/kv/set` → 快照 → 界面）。

这样至少覆盖了三件真形状才会暴露的事：

| 覆盖点 | 断言 |
| --- | --- |
| 两个键并成**一个**还原点 | 界面上「2 个存档」（裂成两行就是「同一时间存了两次」） |
| 大小按 KB 显示 | `2 个存档 · 2 KB`（不是「1734 字节」） |
| 预览按 key 分块 | `settings …` 和 `save …` 各一段 |

顺带修掉两处**探针自己的**按下标取值：多键之后 `list` 是 id 倒序，
`safety[0]` / 最新那条不一定是 `save` ⇒ 全部改成按 `key`（或按 `version`）找。
（这类断言在单键时永远绿，加第二个键的当天就红了 —— 和「多了一行」那个坑同源。）

### 7.14.11 改口：「按版本存就行，不需要用户操作」（2026-11-02 晚）

第一版做的是「家长自己存一个还原点」—— 一个按钮，点了给每个 key 各存一份
（`reason: manual`）。家长的原话是：

> 存档系统按版本存就行了。不需要用户自己操作。

这句话否掉的不只是一个按钮，是**这个按钮背后的责任分配**：
「什么时候该存一下」本来是系统能判断的事，摆成按钮就变成家长的一道题 ——
他没点、孩子把存档玩坏了，责任就跑到他头上。所以：

| 去掉了 | 留下了 |
| --- | --- |
| 「现在存一个还原点」按钮（`data-snapshot-save`） | 还原点列表 / 预览 / 退回 / 二次确认 / 回退记录 |
| `saveSnapshotNow()`（前端循环调 `/game/snapshot/create`） | 服务端每次写入后的自动快照 |
| `busy: 'save'` 那个忙态 | `busy: 'restore'` |

**「按版本存」在服务端早就是成立的**（`game_snapshot_srv.go` 的 `MaybeSnapshot`，
`GameStorageService.Set` 里每次写入之后调）：

| 触发条件 | 说明 |
| --- | --- |
| 没有历史 | 第一笔存档必有快照 |
| 距上次 ≥ 600 秒 | 界面上说的「大概十分钟一份」 |
| **字节长度**变化 ≥ 20% | 存档长大 / 缩小时补一份 |
| 每天第一份 | 标 `is_daily_baseline`，**永久保留**（不参与 20 份淘汰） |

每键保留最近 20 份 + 日切基线（`SnapshotKeepPerKey = 20`）。

⚠️ **变化比例只看字节长度**（`changedEnough` 里 `abs(newLen-oldLen)/oldLen`），
   不看语义：`{level:1}` → `{level:99}` 这种「长度差不多的玩法变化」**不会**留快照。
   这不是 bug，但它是「为什么有时候连玩半小时只有一个还原点」的答案。
   真觉得不够，该动的是服务端策略（按版本号存），**不是**把这个按钮加回来。

⚠️ 列表是**挂载时**读的：家长开着详情不动、孩子那头又存了几次，列表不会自己跳。
   这不算缺陷（他回档点的是眼前看到的那一行），但探针要「关掉详情再重开」
   才验得到「看得到新的」。

探针第 2 步因此整段重写（原来点按钮、断言「存好了」）：

1. 断言界面上**没有** `[data-snapshot-save]`，文案里也没有「现在存一个还原点」；
2. 走 `host.storage.set` 写一版**更大**的存档（字节变化得真的超过 20%，否则按策略
   本来就不该留 —— 那是策略不是 bug）；
3. 查库确认多了一份 `reason=auto`、`version` 与刚写的那版对得上的快照，内容就是新那份；
4. 关掉详情再重开（列表是挂载时读的），预览里读到「第 N 版」且「和现在一模一样」。

界面文案也跟着改了：不再提「可以现在手动存一个」，只说
「存档由系统自己按版本留，不用家长动手：大概十分钟一份，存档变化大的时候也会补一份，
每天的第一份会一直留着」—— 这段话和上面那张表是一一对应的，别只改一边。

#### 改这一节时踩到的三个探针坑（都不是产品问题）

1. **`waitForSelector(sel, { state: 'detached' })` 在 puppeteer 25 里不生效。**
   25.x 的 `QueryHandler.waitFor` 只读 `visible` / `hidden`，`state` 被**静默忽略** ⇒
   退化成「等它出现」，于是「等弹层关掉」会死等满超时并报
   `Waiting for selector failed`，看着像「✕ 点不动」。
   实测插桩 `closeHits: 1, dialogs: 0` —— 点到了、也关掉了。**改用 `{ hidden: true }`**。
2. **弹层入场动画没落定时量不到位置。** `anim-sheet-up` 是 `translateY(100%) → 0`（约 280ms），
   而 `getBoundingClientRect()` **含 transform** ⇒ 刚重开详情就点，rect 是
   `30,859 330x32`（视口 844 高），`elementFromPoint` 返回 `null`，
   报「点不到」。`tap()` 因此改成**重试**（滚动 + 等两帧 + 命中测试，最多 10 次）。
3. **`JSON.stringify` 比存档内容会假红。** 服务端存 JSON 文本、读回来是 Go 的
   `map[string]interface{}`，序列化时**键按字典序重排** ⇒
   `{"coins":55,"level":2,…}` ≠ `{"level":2,"tag":"v2",…}`。
   探针加了 `sameJson()`（递归按键排序后比），三处比较都换掉。
   ⚠️ 以前能过是因为 `{level, tag}` 本来就有序 —— 换一个字段顺序就会红。


### 7.14.12 回档记录要说清「退回到了哪一份」（2026-11-02 深夜）

原来那一行写的是「今天 21:30 退回了以前的版本」—— 家长刚点完一个还原点，
回头查记录，看到的是**一句等于没说的话**：他不知道退到了哪一天，
也就没法判断「是不是退错了一份」。

#### 为什么不是「显示第 3 版」

`from_version` / `to_version` 接口里一直有，但家长脑子里没有「版本号」这个概念，
只有「昨天下午那个点」。而且回档是按**时间点**做的（`restore-by-time`，§7.14.2），
他自己点的就是「今天 21:30」那个还原点 ⇒ 记录里就该是那个时间。

所以加的是 `target_at`（**被恢复那份快照的创建时间**，Unix 秒），
界面读成「今天 21:30 退回到了今天 21:30 那份（家长回档）」。

#### ★ 关键决定：时间要在**回档那一刻落库**，不能列表时现查

第一版是 `gorm:"-"` + 列表时按 `snapshot_id` 现查 —— 看着很省事（不用加列、
不用迁移），但它有个**会自己烂掉**的性质：

- 快照会被保留策略淘汰（每个 key 只留最近 20 个 + 日切基线）；
- 淘汰之后 `snapshot_id` 还在日志行里，但那份快照已经查不到了；
- 于是**过几天再打开，所有历史记录又退回「以前的版本」**。

修好的东西随时间退化，而且**不报错**——只有真的过几天回来看才发现。
现在改成 `target_at` 是真列，`Restore` 在事务里用 `snap.CreatedAt` 写死；
列表时只在 `target_at == 0`（加列之前的老行）才去回填一次，
回填不上就还是 0，界面退回旧说法。

`TestRestoreLogTargetAtSurvivesPrune`（`game_snapshot_srv_test.go`）就是钉这件事：
回档 → **物理删掉那份快照**（`Unscoped().Delete`，模拟保留策略淘汰）→
读日志，`target_at` 必须还在。

#### 界面上的三种写法（一种都不能显示成 1970）

| `target_at` | 界面 |
| --- | --- |
| `> 0` | 今天 21:30 退回到了今天 21:30 那份（家长回档） |
| `== 0`（快照已淘汰） | 今天 21:30 退回到了以前的版本（家长回档） |
| 忘了判 0 直接格式化 | **今天 21:30 退回到了 1970 年 8:00 那份** ← 不报错、有字、全错 |

第三种是这一带最典型的静默错误（`new Date(0)` / 秒当毫秒），
所以探针里专门有一条 `!/1970/` 的断言，不是只断言「有字」。

#### 验收（当时 39 条，比原来多 7 条；§7.14.13 又加了 2 条 ⇒ 现在 41 条）

```bash
node scripts/_probe-snapshot-online.mjs
```

新增的判据是**「等于」不是「大于」**：

- 服务端 `restore-logs` 的 `target_at` **等于**那份快照的 `created_at`
  —— 只断言 `> 0` 抓不到「取成了回档动作自己那份快照的时间」（差一秒，看着像对的）；
- 界面最新一行是「退回到了 … HH:MM 那份」；
- 最新一行**不再**出现「以前的版本」；
- 整栏都**不出现** `#40` 这种内部备注（`从快照 #40 回档` 是后台审计用的）；
- 整栏都**不出现** `1970`（补不上时间的老行必须走降级文案）。

#### 一个探针坑：别拿整块容器的文字断言

第一次写的是 `!logText.includes('以前的版本')`，`logText` 取整个
`[data-snapshot-logs]` 的 `textContent` —— **恒红**，而且红得没有意义：
这个账号上还留着以前跑探针时的回档记录，那些记录指向的快照早被淘汰了，
界面只能如实退回「以前的版本」。那不是这次的毛病。

➜ 断言要**按行**取（`$$eval('[data-snapshot-logs] li', …)`），
「文案口径」这类判据看**最新那一行**；只有「不该出现内部备注 / 不该出现 1970」
这种**整栏都成立**的判据才用全量。


### 7.14.13 ★★ 同一秒里落了两份快照（2026-11-02 深夜）

这条是**探针报出来的**，不是读代码想出来的，而且它的表现很有欺骗性：

```
✗ ★ 服务端那份退回成了还原点的内容（不是新那份） — {"level":99,"tag":"v99"}
```

界面预览明明写着「level：99 → 2」，点「确认退回」之后服务端是 **v99**。
单独跑这条探针**绿**，11 条探针连着跑**红**。当时第一反应是「探针有时序问题」——
错了一半：**探针确实撞上了一个时序窗口，但窗口里漏出来的是产品缺陷。**

#### 坏在哪

`restore-by-time` 的判据是 `created_at <= at`，而 `at` 的粒度是**秒**：

```go
Where("uid = ? AND game_id = ? AND kv_key = ? AND created_at <= ?", …).
Order("id DESC").First(&s)
```

`id DESC` 的意思是「**那一秒里最新的一份**」。而还原点列表是**挂载时**读的：
家长点开详情看了一会儿（孩子那头又存了一次，服务端按策略补了一份快照），
这一份的 `created_at` 可能和列表里那份**同一秒**。于是：

| 界面以为 | 服务端实际 |
| --- | --- |
| 退回到 21:30 那份（第 2 版） | 退回到 21:30:00 里**更晚**写进去的那份（第 99 版） |

两边都不报错，回档记录里写的时间还是「今天 21:30」——**看着完全正确**。

#### 为什么不是「探针等一秒再点」

那样等于把缺陷留在产品里，只让探针不撞上它。真人不会等：
「点开详情 → 犹豫 30 秒 → 点退回去」这个间隔里孩子写一次存档再正常不过，
而 `at` 与写入落在同一秒的概率是 1/2 量级（详情页停留几秒就够）。

#### 修法：`max_id` —— 钉住「界面看到的那批」

`restore-by-time` 加一个可选 `max_id`（界面传 `Moment.maxId` = 这一组里最大的快照 id）：

```
created_at <= at  AND  id <= max_id
```

- **为什么不是传 `snapshot_id`**：一个还原点跨多个 key（`save` + `settings`），
  而「一次调用恢复整个游戏」正是 §7.14.2 定下的入口；传单个 id 就退化成 N 次请求，
  中途失败留一半旧一半新。`max_id` 是**一批行**的上界，正好对应「那一屏」。
- **为什么 `id <= maxId` 等价于「界面看到的那批」**：快照 id 自增，
  列表之后才写进来的行 id 一定更大。所以它不会误伤同一秒里**更早**写进去的行。
- **不传（0）保持旧行为**，老客户端不受影响。

`Moment.maxId` 在 `groupMoments` 里算：这一组 `rows` 的最大 `id`（不是整屏最大 ——
每个还原点各带各的）。

#### 验收：确定性的那条放单测，别放探针

「同一秒两份」是**时序相关**的，探针里复现不了（撞上才有）。所以：

- **Go 单测** `TestRestoreByTimePinsMaxID`：造两份快照，把 `created_at` **直接压成同一秒**
  （`Update("created_at", at)`），断言不带 `max_id` 时退到新那份、
  带 `max_id = old.ID` 时退到 old。去掉仓储里那两行 `if maxID > 0 { … }` 就红。
- **浏览器探针**（41 条，+2）：不撞时序，验**契约**——
  1. 回档请求带上了 `max_id`（`page.on('request')` 里读 body，界面上看不见它）；
  2. 那个 `max_id` **小于**「孩子后写的那份快照」的 id（界面没看到的不在范围里）。

第 2 条是关键：只断言「带了 `max_id`」抓不到 `restoreToMoment(…, 0, …)`
这种「参数传了个 0 也不报错」的写法。

#### 排查记录：这条红其实是**磁盘满**假扮的（别踩第二次）

中间有三次「点了没反应」——`tap` 的 `elementFromPoint` 明明命中了按钮，
点完预览不展开，死等 15 秒超时。真相是 E: 盘 0 字节可用：

- 后端 `database or disk is full (13)`（登录直接 500）；
- 前端表现是**某个 onClick 之后什么都不发生**（不报错、不弹提示）。

探针每跑一次在 `.e2e-scratch/<probe>/profile-<ts>/` 留一个 ~19 MB 的 chrome 用户目录，
跑十几轮就把盘吃满；而这台机器的删除被接管成「移到回收站」，
`rm -rf` 之后 `df` 一点没变。所以红之前先看 `df -h /e`，
清理走 `python _tools/purge_scratch.py --apply` + `python _tools/purge_scratch_bin.py --apply`
（后者才是真正把空间还回来的那一步）。

> ⚠️ 顺带记一个自己踩的坑：`purge_scratch.py` 曾经是 **0 字节**（写它的时候盘满了，
> 工具报 ENOSPC，但脚本「运行成功、目标 0 条」看着像没东西可删）。**空脚本会伪装成成功。**


## 7.15 在线版：两张「会当场打脸」的卡（2026-11-02 晚）

「从备份恢复」和「清空全部数据」在本地版是正当能力 —— 数据就在这台设备的
Dexie 里，导入 = 覆盖它，清空 = 删掉它。搬到在线版，两个都坏了，而且坏法是
同一种：**先承诺、再当场否认**。

### 7.15.1 坏在哪

| 卡 | 本地版为什么成立 | 在线版为什么坏 |
| --- | --- | --- |
| 从备份恢复 | 导入 = 用文件覆盖 Dexie | 备份里的行 id **没有 `srv_` 前缀**，而 `pullFromServer` 只清 `srv_` 行 ⇒ 导入的那些**留下来和服务端那份叠加**：余额显示成两份之和、任务重复出现；而服务端根本不认这些行 —— 孩子看到一个很大的余额，一花就说不够 |
| 清空全部数据 | 删掉就是删掉 | 清完 Dexie，下一次 `refresh` 又把账号里那份拉回来 ⇒ 提示「已重新开始」，几秒后记录全回来了 |

第二种更糟：它不是「没反应」，是**界面自己打自己的脸**。用户对「说做完了却没做」
的信任损失，比「这个功能没有」大得多。

### 7.15.2 处理：不画按钮，把理由写在卡上

- 新增 `src/online/backup.ts`，只装三样东西：`IMPORT_REFUSAL`、`RESET_REFUSAL`、
  `onlineDataOpRefusal(online, op)`。
- **文案只有一份**：卡片上的段落和 `importBackup` 的返回值用的是同一个常量。
  探针第 6 步直接断言 `store 返回的 message === 卡上那段文字` —— 分两处写，
  改一处忘一处，用户会在「点按钮看到的」和「调试桥看到的」之间读到两种说法。
- **闸门在 store**（`importBackup` / `resetAll` 开头），不只是「界面不画按钮」：
  调试桥、以后的批量脚本、自动化都绕得过按钮（同「门槛放 store，不放按钮」）。
- `resetAll` 从 `void` 改成 `Promise<boolean>`：以前它不管清没清都返回 `undefined`，
  界面照旧 toast「已重新开始」—— 那正是上面第二种坏法的代码形态。

在线版这两张卡现在长这样（`data-backup-import-blocked` / `data-reset-blocked`）：

> **从备份恢复**
> 在线版不能从备份恢复：记录都在账号里，导入的旧账会和账号里那份叠在一起
> （余额显示成两份、任务重复出现）。换设备直接登录同一个账号就行。
>
> **危险操作**
> 在线版的记录在账号里，App 里清不掉 —— 清了下次打开又会回来。
> 要让孩子重新开始，请先退出登录（记录还在账号里，登录就回来）。

两段都**说出了「那怎么办」**（登录同一个账号 / 先退出登录）。只说「不支持」的提示，
家长的下一个动作是「再点一次」或者「问客服」。

### 7.15.3 为什么规则抽成纯函数

`isOnlineMode` 是**构建期常量**（`src/sync/pull.ts`，`vitest.config.ts` 钉成 `local`）
⇒ store 里根本造不出「在线版」来测。规则留在 `onlineDataOpRefusal(online, op)`
就能单测（`src/online/backup.test.ts`，4 条）：

1. 本地版一律放行（导入 / 清空都是本地版的正当能力）；
2. 在线版两条都挡，而且**各有各的理由**（两句话不能是同一句）；
3. 拒绝消息要说出「那怎么办」；
4. 别把内部词漏给家长（`Dexie` / `srv_` / `缓存` / `服务端` / `服务器`）。

第 4 条不是洁癖：第一版文案里写了「服务端」，家长读不懂这个词，只会读成
「坏了，要找人修」。

### 7.15.4 导出没跟着砍

「导出到文件」是**只读**的（读 Dexie 生成 JSON），不参与恢复，也不会和服务端打架 ——
在线版反而更该留一份底稿（换设备、账号出问题时的唯一凭据）。所以只把说明换成
在线版口径（「记录本来就在账号里，换设备登录就有 —— 导出只是自己留一份纯文本底稿」），
按钮留着。

### 7.15.5 验收

```bash
node scripts/_probe-data-ops-online.mjs http://127.0.0.1:4406/    # 20 条断言
```

七步：记数据量 → 进「💾 数据」栏 → 查「从备份恢复」卡 → 查「危险操作」卡 →
查文案没漏内部词 → 从调试桥调 `importBackup` / `resetAll` → 核对本地和服务端都没变。

判据里有三条值得单说：

- **连隐藏的 `input[type=file]` 都不许留**：留一个在 DOM 里，调试桥和自动化照样能
  往里塞文件，绕开「不提供」这件事。所以断言的是 `input[type=file]` 个数为 0，
  不只是「按钮文案不在」。
- **「确认清空」也不许出现**：只删掉第一颗按钮、留下二次确认，等于让用户点进去
  才发现不行 —— 比没有更糟。
- **拒绝要真拒绝**：`resetAll()` 返回 `false` 还不够，还要核「伪造任务没进本地、
  任务条数没少、服务端钱包没变」。返回值和副作用是两件事。

⚠️ 探针进「数据」栏要 `protectParentActions: false`：这一栏压在家长密码后面
（`dataGateOpen = !protectionOn || !dataLocked`），和快照探针同一口径。
⚠️ 端口别用 4401 / 4405（常年被旧 preview 占着，`curl` 照样 200 ⇒ 探针跑在别人的构建上）。

### 7.15.6 本地版一个字没变

这两张卡在本地版还是原样（`📂 选择备份文件` / `🗑️ 清空全部数据` + 二次确认），
`scripts/e2e-wipe.mjs` 和 `e2e-check.mjs` 第 9c 段照旧只对**本地版**有意义。
在线版跑那两个脚本必然是红的（按钮不存在）—— 那不是回归，是模式不同。

### 7.15.7 已知没做的

- **真正的「换账号迁移」**（把旧账号的账搬到新账号）：要服务端有迁移接口，
  这一期没做。现在能给的只有「登录同一个账号」。
- **真正的「清空账号」**：同理。现在能给的只有「退出登录」（记录留着）。
- **钻石不上云**（有意留着，见下面那段）：本版里钻石**只进不出** —— 发放入口
  （家长栏的钻石卡）和花它的入口（游戏商城的购买按钮）都已经从界面撤掉，
  唯一来源是「全新档案赠送 500」。所以它是个**装饰性余额**，不会出现
  「界面有、服务端没有 ⇒ 花不掉」那种问题。真要恢复钻石经济，顺序必须是
  **先**有服务端发币接口（带家长 PIN 校验，否则孩子能自己发）→ 购买走
  `/api/game/purchase`（服务端已支持扣钻石 + 发所有权）→ 最后才谈把本机
  那 500 搬上去。反过来做等于把「界面承诺了它做不到的事」写进账本。
- ~~老设备上的兑换券余额还没迁移~~ —— 已做（§7.15.8）：`POST /api/wallet/import`，
  首次登录自动结转。

真要动手时，接口大概长这样：`POST /api/account/import`（带幂等键 + 全量校验）与
`POST /api/account/reset`（软删 + 留一份 `before_reset` 快照，可回滚）。
两件事都必须**在服务端做**，客户端的 Dexie 只是缓存 —— 这是这一节的全部结论。
（结转那半已经按这个思路做了，只是挂在 `/api/wallet/import` 上：它本来就是钱包操作，
不新开路由组，也不用动 wire。）

### 7.15.8 从本地版升级上来：旧账要**搬上去**，不是算进余额（2026-11-03）

本地版和在线版共用同一个包名、同一套表。从本地版升级上来的设备，`ledger` /
`harvestLedger` 里还留着旧行；而余额是**整表求和**（`currentBalance` 等，
不过滤 `srv_` 行）⇒ 界面显示「服务端 + 本机旧账」。

实测（探针，2026-11-03）：服务端 `points=219`，往本机插一行 `+1000` 之后
界面显示 **1219**，重开 App 还是 1219。孩子看到 1219 分，兑换时被服务端拒掉，
而且只说「积分不够」—— 这类「两个都对、加起来不对」的问题，四层验收全绿也看不见。

#### ① 三条路里选了「搬上去」

| 做法 | 结果 |
|---|---|
| 什么都不做 | 界面虚高，花不掉，不报错 |
| 只让界面只算服务端那份 | 数字对了，但孩子的分**看起来**没了 |
| **搬上去（选定）** | 分数无缝延续，两边只剩一个事实 |

#### ② 只搬余额，不搬流水

逐条搬等于让两边各持一套「同一个事实」的账：重试一次就可能多记一笔，而本地流水
里的 `refId`（任务实例 / 农场对象）在服务端根本不存在。所以每种币最多写一行
「从本地版结转」，来源 `legacy_import`，备注带笔数。

#### ③ 幂等键 = 安装 id + 载荷

同一份载荷重试 ⇒ 命中同一把键（服务端按 `(uid, key, 币种)` 去重），不会多记；
载荷变了（上次只搬了积分）⇒ 另一把键，把差额补上。换一台设备也有自己的安装 id，
不会互相吞掉。

#### ④ 顺序：先搬、再拉、后删

`pullOnce` 里 `adoptAccount` 之后、拉取之前调 `importLegacyIfNeeded`：

1. 数出本机非 `srv_` 行 → 调接口 → **成功了才**删那几行（按 id 快照删，不整表删）
2. 紧接着这一趟拉取把服务端那份（含刚搬上去的）读回来

★ 失败**不删**本机行，并记 `legacy.importPending` 让下次刷新重试 —— 否则断网那一次
没搬成，就永远搬不成了。★ 顺序反了会短暂显示「余额突然变少」。

#### ⑤ 只管积分和兑换券

钻石（`mallLedger`）在在线版里**根本没上云**（见 `mintMall` 的注释），搬一个界面上
看不见的余额没有意义 —— 那是另一件事，别顺手做。

★ 判据：`online/legacy.test.ts` 8 条 + 探针 `scripts/_probe-legacy-import.mjs`
（全新 profile → 先不登录插一行旧账 → 注入 session 重开 ⇒ 服务端余额含这笔、
界面 == 服务端、本机行已删、再重开不翻倍）。**变异验过**：把结转整个关掉 ⇒
探针红 4 条，其中「界面余额 == 服务端」读到 `store=1219 服务端=219`。

## 7.16 断网时界面说什么（2026-11-02 深夜）

在线版的读路径是「服务端 → Dexie → UI」，而**拉取失败不抛**（没网也要能进 App）。
于是界面会安静地显示旧数据 —— 这是四层验收全绿也看不见的一类问题：

- **老设备**：昨天同步的任务和余额，看着像今天的；
- **新设备**：一片空白 —— 孩子只会说「我的任务都不见了」。

两种都会被当成「数据没了」，而不是「网络断了」。而「数据没了」会让人去重装。

### 7.16.1 只加一句话，不拦任何东西

`components/SyncBanner.tsx` 挂在 header 和 main 之间（**全局状态，不属于任何一个 tab**
—— 挂在页面里的话，孩子切到别的页就看不到，正好在那一刻以为数据是新的）。

两句话分开写，因为**该做的事不一样**：

| 情况 | 界面 |
| --- | --- |
| 从来没同步成功过 | 连不上服务器，这台设备还没有同步过内容。检查一下网络，再点「再试一次」。 |
| 有旧数据 | 连不上服务器。你看到的是**今天 21:40** 同步的内容，新的任务和积分要等网络好了才出现。 |

它**不拦**任何操作：写操作自己会弹「刚才那一步没有生效」（`online/write.ts`），
在这里再拦一道，连「看一眼今天的任务」都做不到了。

`failure` **要记 `no-session`**（2026-11-03 改）。原来不记是因为「没登录是登录闸门
的事，说『连不上』会指错方向」；闸门拆掉之后，在线版启动会自动建游客账号，
拿不到会话只可能是**连不上服务器** —— 这时候不说，孩子看到的就是一整套空界面，
而屏幕上什么都不说。

### 7.16.2 ★★ 「上次同步是几点的」必须落库

第一版把 `lastOkAt` 只放在内存里 —— 探针第一次跑就红了：

```
✗ 重开之后仍然知道「上次同步是几点的」（不是「还没同步过」）
```

一重开 App 内存就清零，于是界面会说「这台设备还没有同步过内容」，
**而 Dexie 里明明有昨天的数据**。那句话比不说更糟：它把家长推向重装。

现在写进 Dexie `meta`（键 `sync.lastOkAt`），只在还没拿到过的时候读一次库。
⚠️ 它是**设备本地状态**（「这台机器上次连上过没有」）⇒ **导出时剥掉**，
不然跟着备份跑到另一台设备上，那边会显示一个它从来没发生过的同步时间。

### 7.16.3 验收（11 条）

```bash
node scripts/_probe-offline-banner.mjs
```

- 能连上时**不显示**横幅（常驻会把真正的提示淹掉）；
- 断网重开 ⇒ 横幅出来，且**仍然知道上次同步是几点的**（这条钉的是 7.16.2）；
- 不说「还没有同步过内容」、不显示 1970；
- 旧数据还在（不是白屏）；
- **还断着网就点「再试一次」，横幅不许消失** —— 这是最容易做错的一条：
  按钮点了就收起横幅，等于告诉用户「好了」，而其实一个请求都没成功；
- 网络回来点一下 ⇒ 横幅自己消失、`failure` 清空。

⚠️ 「断网」用**拦截 `/api/` 请求**模拟，不用 `page.setOfflineMode(true)`：
后者连页面自己的 JS 都拦掉，`reload` 直接 `ERR_INTERNET_DISCONNECTED`，
验的就不是「服务端连不上」而是「整页打不开」。

⚠️ 横幅外层**不能**写 `px-4`：内层用了 `pl-safe pr-safe`（= `env(...) + 1rem`），
两个一起写会叠成 2rem（`styles/theme.css` 里 `pl-safe` 那条注释说的就是这件事）。

## 7.17 并发 refresh 会把「刚写进去的」折叠掉（2026-11-02 深夜）

`refresh()` 一直有个并发闸门：并发的调用**折叠成一次**。理由写在注释里，
是对的 —— 各自基于同一份快照推算「缺失的实例」再一起写，会出现同一天两条实例。

但「折叠成一次」有个前提没写下来：**那一次读的是它发起时的服务端状态**。
于是出现这么一条链：

```
家长点「已经买好了」
  → wishConfirm  → 服务端 committed→confirmed，然后 refresh()（A 起飞）
  → wishDone     → 服务端 confirmed→done，然后 refresh()（B 被折叠进 A）
  → B 拿到的是 A 的 promise：A 读到的是 done **之前**的状态
  ⇒ 服务端已经是 done，界面还写着「待确认」，而且不报错
```

它是探针抓到的：`本地那单也是 done — doneAt=undefined`。**三次里红一次** ——
时序窗口很小（两次 refresh 挨得够近才折叠），但真人点「已经买好了」就是连着的。

### 修法：折叠成一次，然后**再补一次**

```ts
if (refreshInFlight) {
  refreshAgain = true          // 记一笔
  return refreshInFlight
}
refreshInFlight = (async () => {
  do {
    refreshAgain = false
    await doRefresh(set, get, opts)
  } while (refreshAgain)       // 有人在这期间又来了 ⇒ 再跑一遍
})()
```

所有并发调用等都等**同一个** promise，所以它们看到的都是补跑之后的结果；
`runFarmCommit` 里那句 `if (refreshInFlight) await refreshInFlight` 也自然跟着变严。

### 判据（单测，不靠时序）

`doRefresh` 每跑一遍只读一次 `db.tasks.toArray()` ⇒ **数它调了几次 = 跑了几轮**：

```ts
const spy = vi.spyOn(db.tasks, 'toArray')
const a = refresh(), b = refresh(), c = refresh()   // 三次并发
await Promise.all([a, b, c])
expect(spy.mock.calls.length).toBe(2)               // 一次 + 一次补跑
```

去掉补跑那两行就红在 `expected 1 to be 2`（实测过）。

> 教训：**「合并并发请求」这类优化，一定要问一句「后来那次调用的写入谁负责读回来」。**
> 只合并不补跑，等于把「更晚发生的事实」永久丢掉一次 —— 而丢掉的那一次
> 恰好就是用户刚做的那一下。

## 7.18 APK 的地址：为什么不能放 `.env.production`（2026-11-02 深夜）

APK 的 API 基址是**构建期常量**（`src/api/client.ts` 的默认值 `http://127.0.0.1:8090`），
在手机上 `127.0.0.1` 是「手机自己」⇒ 登录 / 兑换码 / 招商申请全挂，
而界面只会说「连不上服务器」，看不出是地址配错了。所以 `build-apk.sh` 有三道闸门。

### 7.18.1 先发现的一个坑：`.env.production` 会污染探针

`build-apk.sh` 原来的提示是「把地址写进 `.env.production`」。但
**`vite build` 默认 `mode=production`，会自动加载 `.env.production`** ——
而 `npm run build` 就是这个 mode。于是地址一旦写在那儿：

```
npm run build（11 条 e2e 探针的第一步）→ 产物里是**线上地址**
  ⇒ 探针连上线上库，而探针会：注册账号、下单、确认、兑换、回档
  ⇒ 往生产数据里灌测试数据，全程**没有任何报错**
npm run site（官网）→ 「在线体验」指向线上 API
```

所以地址改成放 **`.env.apk`**，只在 `vite build --mode apk` 时加载
（`package.json` 里 `build:apk` = `tsc -b && vite build --mode apk`）。
`npm run build` 永远看不到它 —— 探针、官网、本机预览都还是 127.0.0.1。

顺带加了一条提醒（不拦）：`.env.production` 里如果有非回环地址，打 APK 时会
打一行 ⚠️，说明它会被所有 `npm run build` 加载。

### 7.18.2 三道闸门（都在 `scripts/build-apk.sh`）

| 闸门 | 判据 | 不拦的话 |
| --- | --- | --- |
| ① 地址存在且不是回环 | 没有 `.env.apk` / 是 `127.0.0.1` ⇒ 停 | 装上去「连不上服务器」 |
| ② 必须 https | `--web-only` 除外 | `allowMixedContent:false`，WebView 直接拦 |
| ③ 真请求一次 | `node scripts/check-apk-endpoint.mjs "$API_BASE"` | 形状对了照样连不上（见下） |

第 ③ 道是这次新加的。前两道只看**形状**，而下面这些只有真机才暴露、
症状全都是同一句「连不上服务器」：域名解析不了 / 证书自签或过期 /
反代把 `/api` 转丢了 / 回包是网关的 HTML 错误页 / CORS 没放行 App 的 Origin。

### 7.18.3 自检脚本 `scripts/check-apk-endpoint.mjs`（11 项）

```bash
npm run check:apk                      # 读 .env.apk
node scripts/check-apk-endpoint.mjs https://api.你的域名.com
node scripts/check-apk-endpoint.mjs --allow-http http://192.168.1.9:8090   # 局域网调试
```

它只发**不写数据**的请求（`/api/ping` + 一次故意失败的登录），可以对着生产库跑：

1. 末尾没有多余斜杠；
2. 是 https（`--allow-http` 放行）；
3. **不是回环地址** —— 这条就是「装上去连不上」的头号原因；
4. 能连上（`/api/ping`，10s 超时）；
5. 没被重定向到别处（反代配错会 302 到登录页）；
6. 回包是 JSON 且带 `code`（不是网关的 HTML 错误页）；
7. 业务码 200；
8. CORS 预检 · Android（`Origin: https://localhost`）；
9. CORS 预检 · iOS（`Origin: capacitor://localhost`）；
10. **真实 POST 也带 `Access-Control-Allow-Origin`** —— 预检过了不等于实际响应过了，
    这两处是分别加头的，配错时只有预检那条会绿；
11. 登录接口返回业务错误码（`10010101 用户不存在`）⇒ 鉴权链路是通的。

对着本机跑的结果（10 绿 1 红，**红的那条正是它要抓的**）：

```
✓ 能连上（/api/ping） — HTTP 200
✓ CORS 预检 · Android（https://localhost） — Allow-Origin=https://localhost
✓ CORS 预检 · iOS（capacitor://localhost） — Allow-Origin=capacitor://localhost
✗ 不能是回环地址（手机上那是「手机自己」） — 127.0.0.1 装到手机后只会说「连不上服务器」
```

### 7.18.4 验收（5 个场景，都实测过）

| 场景 | 期望 |
| --- | --- |
| 没有 `.env.apk` | 停在「没有配置后端地址」，提示改成写 `.env.apk` |
| `.env.apk` 是 `http://…`（真打 APK） | 停在「必须是 https」 |
| `.env.apk` 是 `https://api.example.test` | 走到自检，报 `ENOTFOUND` 并停（域名不存在） |
| `.env.production` 有线上地址 | 打一行 ⚠️，**且不拿它当地址**（仍然报「没有配置后端地址」） |
| `.env.apk` 存在时跑 `npm run build` | 产物里仍是 `127.0.0.1:8090`，**不含** `.env.apk` 的地址 |

最后一条是这节的**核心判据**：隔离靠的是「`apk` 这个 mode 名」，不是靠文件放得深。
验法是 `grep` 产物：

```bash
npm run build && grep -c "127.0.0.1:8090" dist/assets/index-*.js   # 1
grep -c "api.example.test" dist/assets/index-*.js                   # 0
```

### 7.18.5 顺手修掉的「构建卡住」

`build-apk.sh` 原来在 build 前有 `find dist -type f -delete`，注释写着「绕过批量删除拦截」。
**恰恰相反**：这台机器把删除实现成**移入回收站**，逐个文件搬 —— dist 里五千多个文件
要跑好几分钟，表现是 `▸ [1/3] 构建 Web 产物…` 之后一动不动（实测 120 秒没完），
看起来像网络卡住 / 构建卡死。删掉这两行，交给 vite 的 `emptyOutDir`（一次 `fs.rm`）。

> 教训：**「绕过安全策略」的写法，要先确认它绕的是哪一层。**
> 逐个文件删除在正常机器上更「可预期」，在这台机器上却是最慢的一条路。

## 7.19 币 → 券：汇率写死 1:1，还绕过了「不开放」的开关（2026-11-03）

`Redeem` 里有一行注释和一行代码互相打脸：

```go
// 汇率：从游戏配置读（voucherPerCoin），这里用默认 1:1
rate := int64(1)
```

配置从来没被读过。后果是两个方向，**都不报错**：

| 情况 | 结果 |
| --- | --- |
| 插件 manifest 里**没写** `voucherPerCoin`（= 不开放，19 款） | 服务端照换不误 —— 等于绕开了作者的开关 |
| 插件写了 2 / 3 | 服务端按 1 发 ⇒ 界面说「换 10 张」，实际到 5 张 |

第二种在客户端只有一条 `console.warn`（`online/coin.ts`），家长看不到。
第一种连 warn 都没有。

### 7.19.1 语义对齐：0 = 不开放

`src/domain/pluginEconomy.ts` 早就定了口径：**`voucherPerCoin` 不写 = 这款游戏不开放兑换**。
服务端现在照抄这一套，`game.voucher_per_coin`：

- `> 0` ⇒ 1 币换 N 张券；
- `0` ⇒ **明确拒绝**，`code = 10041201`（不是静默按 1 发）。

汇率**仍然不接受客户端传**。兑换就是印券，让客户端带汇率等于把印钞机的旋钮
交出去 —— 一个写错的插件传 1000 就能印出无限券，而账本上每一笔都「合法」。
客户端自己算的那份只用来**对账**（对不上会 `console.warn`，那是「该去后台对齐」的信号）。

### 7.19.2 默认 0 的取舍

这一列的默认值是 **0（不开放）**，不是 1。默认 1 等于「没配置的游戏都能印券」。

代价必须写下来：**上线后要先跑一次 seed**，否则本来就开放的两款
（`claw3d` / `prizepark`）会暂时换不了。

```bash
go run ./cmd/seed -c configs/config.yaml games   # 21 款，按 manifest 标 0/1
```

好在失败是**看得见**的（`10041201 这款游戏没有开放兑换`），不是静默少发。
本地库跑完的结果：`claw3d` / `prizepark` = 1，其余 19 款 = 0。

### 7.19.3 判据

**单测（确定性）** `internal/app/service/game_coin_srv_test.go`：

- 汇率 3：2 币 ⇒ 6 张券、余额 8，且**账本里的余额和响应一致**；
- 汇率 0：报 `10041201`，币没少、券流水 0 条。

**变异验证**（把 `rate := g.VoucherPerCoin` 改回 `int64(1)`）：

```
--- FAIL: TestRedeemUsesPerGameRate
    game_coin_srv_test.go:69: 券数 = 2，应该是 6（2 币 × 汇率 3）
```

**探针** `_probe-coin-online`（44 → **47 条**）：第 7 步加了三件事 ——
绕过 HostApi 直接打接口必须被拒、被拒后余额没变、**账本里没有新的 `game_redeem` 流水**。

### 7.19.4 ★★ 探针自己也踩了两次「假绿」

改完服务端，币探针第一步就红了：它拿 `ropeland` 当「开放兑换」的游戏
（合成 manifest 写 1），而服务端的 `ropeland` 现在是 0 —— 探针撞上了自己刚立的规矩。
换成 `claw3d`（服务端 1）就好了。**教训：探针合成的 manifest 必须和服务端配置一致**，
否则失败信息长得像「换券坏了」。

第二次更隐蔽：把「不开放」的游戏写成 `cloudfarm`，然后断言「币没少」。
可这个账号在 cloudfarm 上**一个币都没有** ⇒ `0 → 0` 恒真；就算把服务端拦截去掉，
兑换也只会失败在「币不够」，账本仍然 0 条。于是：

```
✓ 被拒之后币还是没少 — 0 → 0          ← 假绿
```

换成 `ropeland`（这个账号上有 30 币）之后才真的验到：

```
✓ （前提）这个账号在「不开放」的游戏上确实有余币 — 余额 30
✓ ★ 服务端币余额没变 — 30 → 30
✓ ★ 绕过客户端直接请求，服务端也拒（10041201）
✓ ★ 被拒之后账本里没有新的兑换流水 — game_redeem 流水 15 → 15
```

那 15 条 `game_redeem` 是**修之前**换出来的 —— 账本自己记着这个 bug。
现在它停在 15。

> 教训：**「没变化」的断言，先问一句「基线是不是本来就是空的」。**
> 余额 0 → 0、流水 0 → 0、列表 0 → 0，全都是恒真。
> 加一条「前提」断言（基线必须非空）比多写三条「没变化」有用得多。

## 7.20 家长设置上云：整份 JSON、PIN 上去、用量留下（2026-11-03）

在线版最后一块只在本机的数据是 `meta.settings` 那一行 —— 小名、头像、家长锁 PIN、
音量、限时、农场规则、兑换口径…一共 20 多个字段。它原来只在这台设备上，
换台设备登录就全丢，而**两台设备各自都「对」**（都显示自己的默认值）。

服务端是整份存：`POST /api/user/settings/{get,save}`，表 `user_settings`
（`uid` 唯一索引 + `payload TEXT` + `size` + `version`）。

### 7.20.1 为什么整份存，而不是一列一个字段

`AppSettings` 有 20 多个字段，而且还在加。拆列意味着每加一个字段要改三处：
实体、仓储 upsert 的列清单、映射。漏一处的表现是「家长设了、服务端没存」——
**不报错**，重启后回退。

整份存之后，服务端只校验**形状**：非空、≤ 32 KiB、合法 JSON、顶层是对象
（`user_settings_srv.go`）。客户端加字段不用动服务端，但发上来的必须是对象
（`123` / `[...]` / `"str"` 都拒）。

写是**覆盖**不是合并（`OnConflict(uid).Update(...)`）：本地删掉的键，
写上去之后服务端也不会留着。这条有单测盯着（`覆盖而不是合并`），
因为「合并」看起来更安全，实际上会让删掉的设置永远复活。

### 7.20.2 ★★ 两张清单：**备份剥、云端传**，但理由各不相同

| 字段 | 备份（`stripDeviceLocal`） | 云端 | 为什么 |
|---|---|---|---|
| `parentPin` | **剥** | **传** | 备份会被发到微信 / 网盘，4 位数字肉眼就能用；而云端是家长自己的账号，换台设备要能用同一个 PIN 开门 |
| `gameClock` | **剥** | **传**（节流 + 按天取 max） | 备份是「搬去另一台设备」的介质，带着用量只会让「导入一份玩之前的备份」变成刷额度；云端必须传，否则**重装 App 就把每日限时重置了**（§7.20.3 ④） |

⚠️ 两行现在**恰好长得一样**（备份都剥、云端都传），但理由完全不同：
备份剥是因为「这个文件会离开这台设备」，云端传是因为「账号就是数据源」。
照着其中一处去改另一处之前，先把 §7.20.3 ④ 读完。

⚠️ 这两张清单长得像，但**别「统一一下」**：统一成备份那份 ⇒ 换机后开不了家长门；
统一成云端那份 ⇒ 明文 PIN 跟着备份文件出门。

### 7.20.3 ★★ 四个静默错法，每个都有一道闸

**① 换账号：把上一个人的家长锁推给新账号。**

`signOut` 不清 Dexie（断网也要能退出去），所以同一台设备换账号登录时，
`meta.settings` 里还是上一个人的。而「云端为空 ⇒ 把本机推上去」这条迁移逻辑，
遇到「新账号云端也是空的」就会把**上一个人的小名和 PIN 写进新账号**。

闸门：`meta['settings.owner']` 记住这份设置是谁的。

```
owner 为 null（从没记过，升级上来的老数据）→ 当作自己的，允许推
owner == 当前 uid                        → 允许推
owner 是别人                             → 整份重置成默认值，一个字都不推
```

重置必须连 `gameClock` 一起：留着 PIN ⇒ 新账号被上一个人的锁关在家长区外面；
留着 `childName` ⇒ 新账号看到别人孩子的名字；留着 `gameClock` ⇒ 上一个人
今天玩的时长吃掉这个人的额度。

**② 旧读响应盖掉新写。**

`refresh()` 是并发跑的，`settings/get` 的响应可能比一次 `save` 晚回来。
照用的话，刚存的设置会被上一份读结果盖回本地 meta —— 不报错。

闸门是**两道**。一开始只有 `version` 一道，**不够**（2026-11-03 修）：

| 闸 | 管什么 | 为什么必须有 |
|---|---|---|
| `writeEpoch` | 这次拉取开始之后**写入成功过** ⇒ 旧快照，丢掉 | 真正的判据：这份读是在写之前发出的 |
| `pullSeq` / `appliedSeq` | 有**更晚发起**的拉取已经落地 ⇒ 这次作废 | 两次读同时在路上，回来的顺序不保证是发出的顺序 |

⚠️ **别用服务端的 `version` 当判据。** 那个号是客户端自己传上去的
（`oSaveSettings` 发 `lastVersion + 1`），而 `lastVersion` 每个进程从 0 开始
⇒ 跨进程、跨设备**不可比**。实测连跑两轮探针，服务端 version 从 `999 → 1 → 2`；
真换台设备就会得出「B 刚存的那份比 A 手上的旧」⇒ A 一直 `stale`，
直到它自己重启才恢复。

⚠️ `writeEpoch` 的取样点必须在**函数入口**，不能紧贴 `settingsGet()`：
前面那句 `getMeta` 走的是 IndexedDB，比一次写请求慢得多 —— 取样点放在后面，
写入会先落地，闸门等于没有（实测仍然 `applied`）。

★ 判据：`src/online/settings.test.ts` 的两条 —— 「读请求在写之前发出 ⇒ 丢弃」
（服务端回 999，本地计数器是 1，旧代码判 `999 >= 1` 就照用了）与
「两次拉取并发、后发的先回 ⇒ 先发的作废」。两条都做过变异测试
（删掉闸门即红）。

**③ 断网时「界面新值、重启旧值」。**

写穿是「服务端成功了才落本地」。失败时**内存也得退回去**，否则家长看着是新值、
下次打开变回旧的。但只能**在内存还是这次那份时**退（`get().settings === next`）——
无条件回退会把家长刚接着打的下一个字吞掉（和 `updateSettings` 头注释里那个
「同一 tick 两次调用」是同一个坑）。

**④ `gameClock`：既要上云，又不能跟着「写穿」走。**

`GamePlayGate` 每 60 秒 `updateSettings({ gameClock })` 落一次盘。它是**限时**这道
闸的执行依据，于是三个要求互相打架：

| 要求 | 不做会怎样 |
|---|---|
| 必须上云 | 重装 App / 换台设备 / 清一次缓存 ⇒ **每日限时重置**，孩子发现重装就能重来 |
| 不能一分钟一个 POST | 请求打满（每 60 秒一次） |
| 不能走写穿 | 写穿是「服务端成功才落本地」⇒ 断网时本地也写不进去 ⇒ 时长不累计 ⇒ **孩子无限玩** |
| 拉取不能直接用云端那份盖 | 本机玩到 25 分钟、云端还是 20 分钟，拉一次退回 20 ⇒ **额度永远用不完** |

闸门是三条，各管一件事：

1. `isUsageOnly(patch)` —— 只碰用量的改动走 `pushUsageBestEffort`：
   **本地先落盘**（时钟必须一直走），网络尽力而为，失败**不回退、不弹提示**。
2. `shouldPushUsage(clock)` —— 累计多 5 分钟才推一次；跨天必推
   （否则云端永远停在昨天，换台设备拉下来就是「昨天玩满了」）。
3. `mergeGameClock(local, cloud, dayStartHour)` —— 同一天取 **max**。
   取云端那份 ⇒ 额度用不完；两份相加 ⇒ 两台设备同时在玩时同一段时间算两遍。

⚠️ 「失败不回退」是这条链上最容易写错的地方：它和普通设置的写穿语义**相反**，
而且反得对 —— 普通设置回退是因为「界面上是新值、重启变旧值」；
用量回退等于把时钟拨回去，直接放开额度。

### 7.20.5 探针自己的三个坑（都当场踩到了）

1. **端口不在 CORS 白名单** ⇒ 预检 403，浏览器只说「连不上服务器」，
   于是「写穿坏了」「断网提示坏了」全红。加 `http://127.0.0.1:4407` 到
   `_goprobe/config.8090.yaml` 的 `AllowOrigins` 并重启后端才对。
   **换端口就要同步这一处**（这条已经踩过三次了）。
2. **`finally` 里的 `process.exit()` 会吞掉未捕获异常**：中途 `TypeError` 时，
   输出看起来像「跑完了、还全绿」，只是断言少了几条。加了 `catch` 打一行
   「探针中断」之后才看见真因（`__kqf__.setState is not a function` ——
   调试句柄只暴露了 `getState`）。
3. **「断网后回退」这条恒真**：如果写穿在 ② 就失败了，断网前后名字根本没变过，
   断言当然过。加了「前提：断网前 store 里必须是刚写上去的名字」才有效。
   同一条规矩见 §7.19.4 —— **「没变化」的断言先问基线是不是空的**。

### 7.20.7 切回前台：重拉数据 + 重读设置（2026-11-02）

`App.tsx` 里那条 `visibilitychange` 监听原来只调 `tick()`，注释写着「从后台切回
前台时刷新一次，避免显示过期数据」—— **这句话一直是假的**：`tick()` 只在
**跨逻辑日**时才 `refresh()`（`store/useApp.ts` 的 `tick`）。所以平板放一边半天
再拿起来，看到的还是半天前的任务和积分，家长在**另一台设备**上改的 PIN /
每日限时也要等到重启或跨日才生效。全都不报错。

#### ① `refresh()` 不会把设置读进 store

`refresh()` → `pullFromServer()` → `pullSettings()` 只做一件事：把云端那份
**写进 Dexie 的 `meta`**。store 里的 `settings` 还是旧的那份 —— `refresh()` 一
开头就是 `const { settings } = get()`，**不重读**（备份恢复那里也踩过同一个坑，
见 `restore` 的注释）。

所以「切回前台只加一个 `refresh()`」会得到一个**一半对**的结果：任务和积分是
新的，PIN 和每日限时还是旧的 —— 比现在更难查，因为「有些东西同步了」。

⇒ 新增 store action `reloadSettings()`：`loadSettings()` → 和内存里那份比一遍 →
**不一样才 `set`**（这条会被反复调到，一次 `set` 触发一整轮订阅）。
`boot()` 原来那段「refresh 完再重读」的内联代码也换成它，两条路径不会再漂。

#### ② 30 秒闸门，不是实时

`src/sync/foreground.ts` 的 `shouldRefreshOnForeground(lastAt, now)`：`lastAt = 0`
（本进程还没拉过）一定拉，其余满 30 秒才拉。来回切 App（回个消息再切回来）很
常见，每次都打一轮接口没必要。

| 想要的效果 | 现在能不能 |
|---|---|
| 切回来看到最新任务 / 积分 | 能 |
| 另一台设备改了 PIN / 限时，这台切回来就生效 | 能 |
| 另一台设备改了，这台**放着不动也会自己变** | **不能** —— 没有轮询也没有长连接，App 必须切到前台 |

最后一行是有意留的：真要推送得加长连接，而孩子的平板一天里绝大部分时间是黑屏
的，长连接只会白耗电。

#### ③ 顺序不能反

`await refresh()` 之后才 `await reloadSettings()`：后者读的是前者刚写进 Dexie 的
那份。反过来读到的还是旧设置。

★ 判据在 `useApp.test.ts` 的 `reloadSettings` 两条：一条断言「Dexie 变了 store
跟着变」（把实现改成空函数就红 —— 实测过），一条断言「没变化时还是同一个对象」
（用 `toBe`，`toEqual` 抓不到「多 set 了一次」）。

#### ④ 探针里数「打了几轮」必须先等静默

`scripts/_probe-settings-online.mjs` 的 ⑧ 用 `page.on('request')` 数
`/user/settings/get`。第一版是「dispatch 完等 1.5 秒再数」，**连红两次** ——
一轮完整拉取要 800ms 上下，上一轮的尾巴正好落进下一个窗口，看起来像闸门没生效。
改成「连续 2 个 600ms 采样都没有新请求」再开始数。

（先量了一遍才敢改断言：直接调 `refresh()` = 1 轮、直接调 `tick()` = 0 轮、
dispatch 一次 = 1 轮 —— 说明多出来的那一次不是我的处理器打的。）

★ 这条断言用**变异**验过不是空转：把 `FOREGROUND_REFRESH_GAP_MS` 改成 0、
把 `await reloadSettings()` 改成 `void reloadSettings` 重新构建 ⇒ ⑧ 一次红 3 条
（store 没跟上 / 打了两轮 / 第二次切又打了一轮），改回来就全绿。

## 7.21 换账号：先清上一个人的缓存，再拉（2026-11-03）

在线版的读路径是「服务端 → Dexie → UI」。换一个人登录时，**在他第一次拉取
完成之前**，界面读到的还是上一个人的任务、积分流水、兑换记录、心愿单。
这不是「闪一下」：拉取失败（没网）时它就一直是那个人的数据 —— 孩子会照着
别人的任务去做，家长会看到别人的心愿单。

### 7.21.1 清理放在「发请求之前」

`src/online/adopt.ts` 的 `adoptAccount(uid)`，在 `pullOnce` 的**第一个 await**
调用（不是请求之后）。顺序错了的话断网就永远清不掉 —— 这条有专门的用例卡住
（`pull.test.ts` 里「换人 + 网络失败：上一个人的行仍然被清掉」）。

三种结果，含义不同：

| 结果 | 含义 | 做什么 |
|---|---|---|
| `first` | 这台设备第一次登录 | **不清** —— 从本地版升级上来的孩子，存档还在本地行里 |
| `same` | 同一个账号 | 什么都不做（每次刷新都走这里） |
| `switched` | 换人了 | 先清云端镜像，再记新 uid |

### 7.21.2 ★★ 只清「云端镜像」，本地行一行不动

本地版和在线版**共用同一套表、同一个包名**（`com.kidquestfarm.app`）。
这里要是 `clear()` 整张表，切回本地版时孩子的数据就没了，而界面上看不出来。

- 带 `srv_` 前缀的行 ⇒ 删（只可能来自服务端）
- `redeemItems` / `wishOffers` ⇒ **整张清**（主键是服务端给的字符串，分不出前缀；
  而在线版里这两张表只可能有云端数据 —— 播种在在线模式下不写）
- `gameKv` 的 `__coin` 镜像 ⇒ 删（余额是上一个人的）
- 其余（本地任务 / 本地积分 / 农场 / 设置）⇒ **一行不动**

### 7.21.3 ★★ 不能复用 `settings.owner`

那个 key 管的是设置（§7.20）：发现换人就整份重置。这里要是也写它，
`pullSettings` 会以为「刚才是同一个账号」，于是把上一个人的 PIN / 昵称
**推到新账号上**。所以另开一个 `data.owner` —— 两件事必须各用一个 key。

### 7.21.4 验收

- `src/online/adopt.test.ts` 6 条：没登录不动 / 同账号不重复清 /
  首次登录不清 / 换人清干净 / **本地行留下** / 清两遍第二遍是 0
- `src/sync/pull.test.ts` 追加 2 条：换人 + 断网仍然清掉；同账号重拉不清
- 三个变异都变红：① `uid` 写成 `id`（`ApiUser` 的字段是 `uid`，
  写错会恒为 undefined ⇒ 永远当成没登录 ⇒ 永不清）② 认领挪到请求之后
  ③ `clearCloudMirrors` 变成空操作

> 第 ① 个是真踩到的：`getSession()?.user.id` 编译得过、测试也可能全绿
> （单独测 `adoptAccount` 时它不经过这一行），只有「换人 + 断网」那条
> 集成用例能抓住它。

## 7.22 在线版：先登录，再引导（2026-11-03）

回归跑 12 个线上探针时，`_probe-login-gate` 连红两条：登录按钮
`elementFromPoint` 命中的不是它自己，点开也没有登录弹层。

查下去不是「按钮画歪了」，是**新手引导压在登录闸门上面**：

| 层 | 来源 | z-index | body 里的顺序 |
|---|---|---|---|
| 登录闸门 | `OnlineLoginGate`（Portal） | 60 | 先挂 |
| 新手引导 | `SetupWizard`（Portal） | 60 | **后挂 ⇒ 在上面** |

同 z-index 时后挂的赢。而引导是不透明 `bg-paper` 全屏，所以用户看到的是引导，
登录按钮**在它底下、点不到**。

### 真正的问题不是层级，是顺序

就算把 z-index 调过来也还是错的：引导「完成」时要写小名 / 头像，而在线版的设置是
**写穿**的 —— 没登录 ⇒ 写不上去 ⇒ 回退 + 提示，`onboardingDone` 永远落不下来
⇒ 下次启动又弹一遍。而且新设备登录一个**已有账号**时，引导填的东西会被云端那份
覆盖掉，白填。

⇒ 在线版没登录时**不决定**引导这件事（`gateDecided` 不置位），等登录之后这个
effect 再跑一遍，那时候按 `onboardingDone` 决定。本地版没这个顺序问题，照旧。

★ 判据：`_probe-login-gate.mjs` 那两条 `elementFromPoint` / 「点开是登录弹层」
（修完即绿）。★ 顺带记一条：**12 个探针连着跑会撞服务端限流**
（`_probe-wish-online` 报 `too many requests`），单跑就绿 —— 别把它当回归。

### 后续（2026-11-03）：闸门本身拆了，但这两条教训还成立

登录闸门换成了自动游客账号（见 §7.8），所以「引导压在闸门上面」这个具体
问题不存在了。但下面两条**仍然要守**：

1. **`elementFromPoint` 才是「点得到」的判据** —— `el.click()` 不走命中测试。
   `_probe-guest-entry.mjs` 里那条「保存进度按钮真的点得到」用的还是它。
2. **引导会盖住顶栏下面的一切**，包括新的「临时账号」横条。所以探针里仍然
   要先 `updateSettings({ onboardingDone: true })` **再重载**才能点到横条。

### ★★ 同一个坑的第二层：闸门自己盖住了自己的弹层

顺序修完，反向那条（`_probe-login-gate`：按钮点得到）绿了。但**正向没验**：
登录之后引导还出不出现、保存能不能落到账号里 —— 这是最容易反向坏掉的地方
（引导永远不出现，而且不报错）。写 `_probe-onboarding-order.mjs` 去验，
第一次跑就红在一个新地方：登录按钮**填得出值、查得到位置、点了没反应**。

原因还是「全屏层赢命中测试」，只不过这次是闸门**自己**：

| 层 | 来源 | z-index |
|---|---|---|
| 登录闸门 | `OnlineLoginGate` | **60** |
| 登录弹层 | `LoginSheet` → `BottomSheet`（**自己又 Portal 一次**） | 50 |

`BottomSheet` 不能留在闸门里（页面外壳的 `anim-fade` 会把它关进小盒子，
见 `Portal.tsx`），所以它和闸门成了 body 下**两个平级的 `fixed` 层**。
父子关系在 DOM 里已经断了，谁在上面只看 z-index：60 > 50 ⇒ 弹层整片被闸门那张
不透明 `bg-paper` 盖住。用户看到的是「点了登录什么也没发生」。

⇒ 闸门改成 `z-[45]`：**高于底部导航(30)、低于弹层(50)**。
闸门的职责只是「盖住 App 外壳」，不需要盖住弹层。

★ 教训：写「全屏层里再弹一层」之前先看两层的 z-index，尤其是弹层**自己会
Portal 出去**的时候 —— 那时候父子关系不作数。
★ 判据：探针里加一条 `elementFromPoint`（按钮中心命中的必须是按钮自己）。
它比「点完看结果」早一步，也直接说出「谁盖住了谁」。

### 正向那一半：登录 → 引导 → 写穿

`_probe-onboarding-order.mjs` 五步：

| 步 | 断言 |
|---|---|
| ① | 未登录：闸门在、`[data-step]` **不在**（引导不能先出来） |
| ② | 走**真界面**登录（不是注 session）：只有一个可见密码框、两个字段都填上、按钮不是 disabled、命中测试是它自己 |
| ③ | 登录后引导**出现**，从 `welcome` 开始 |
| ④ | 小名输入框换成新名字 → 进 `done` |
| ⑤ | 服务端 `/user/settings/get` 的 `childName` **等于新名字**（写穿成功） |

四个当场踩到的坑：

1. **按钮 `disabled` 时点了等于没点。** 密码没填进去 ⇒ `canSubmit` 为假 ⇒
   `clickByText('登录')` 命中的是那个 disabled 的按钮，什么都不会发生，
   最后红在「闸门没摘掉」，看着像登录接口坏了。要先
   `waitForFunction(() => !btn.disabled)` 再点。
2. **`input[type=password]` 写在双引号里会被 bash 吃掉**（`command not found`），
   补丁静默变成空操作 —— 改完立刻 `grep` 一遍。
3. **小名输入框是预填的**（云端已有小名），`page.type` 会追加成
   「宝贝引导30921」；三击选中在这台机器上没生效，改用 `Ctrl+A` 再打。
4. **探针会临时把账号的 `onboardingDone` 改成 false**（模拟新账号），收尾写回。
   写回时版本号要**读当前值再 +1**，别写死一个常数 —— 写死就看不出
   「这次到底写进去没有」（而且会把服务端的号按回去）。
