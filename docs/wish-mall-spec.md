# 心愿商城 设计

> 2026-10-28 起草，同日按用户口径重写为 v2。
>
> **v3（2026-10-29）**：付款规则改成**券 + 积分混付**，和「兑换」模块一字不差
> —— 券先花、不够用积分补、1 券 ≡ 1 积分。用户原话：「就跟兑换模块一样的，
> 可以用兑换券和积分兑换」。v2 里「只用兑换券、不混付积分」那条**已作废**。
>
> **v2 的核心变化**：心愿商城不是「兑换」的扩展，而是一个**独立的 tab**。
> 它卖的是**外面世界的东西**（合作商商品 + 游戏），成交发生在
> **淘宝/天猫/京东/闲鱼**，App 只做「意向 → 定价 → 兑换 → 引导购买」这条链。
>
> **v4（2026-11-05）**：底栏从五格回到四格 —— 心愿仍然是独立一格，
> 但**「积分」那一格没了**。用户原话：「积分是不是换个地方更好，主要是挤占了下边栏，
> 下边栏 4 个为好。」明细改从**顶栏那颗 🪙** 点开一层整屏页（`data-points-sheet`）。
> 所以「心愿是第几格」这个问题，从 v4 起答案是**第 4 格**（任务 / 游戏 / 兑换 / 心愿）。

---

## 0. 一句话

**孩子用兑换券表达想要，家长用兑换券定价，成交在 App 外面。**
App 不做收银台，也不代收货款。

---

## 1. 三套币的分工（这是整个设计的地基）

| 币 | 来源 | 去处 | 谁定价 |
| --- | --- | --- | --- |
| **积分** 🪙 | 任务 / 签到 / 农场 | **家庭内兑换**（零食、玩平板、出去玩） | 家长 |
| **兑换券** 🎫 | 农场产出 / 玩插件游戏 | **心愿商城**（游戏、实物礼物），券不够时用积分补 | 家长 |
| **钻石** 💎 | 支付 / 兑换码（**当前仅测试**） | 直接买游戏 / 商品 | 运营 |

**三者之间一条通路都没有。** 这不是约定，是表结构保证的：
`ledger` / `harvestLedger` / `mallLedger` 三张表物理隔离，`currentBalance()`
只看得到 `db.ledger`，`currentHarvestBalance()` 只看得到 `db.harvestLedger`。

> ⚠️ 任何两条币之间的双向通路都是印钞机。加任何新边之前先读
> `types.ts` 里 `HarvestEntry` 那段注释。

**为什么心愿商城以兑换券为主**：兑换券只能靠「玩」和「农场产出」赚，
积分靠「完成任务」赚。心愿商城卖的是玩具和游戏 —— 用「玩出来的钱」买「玩的东西」，
闭环是自洽的。而积分对应的是家长给的日常奖励，用去买 ¥69 的盲盒会让家长觉得
「我发出去的分变成了我的账单」。

> **v3 的取舍（2026-10-29，家长拍板）**：券**不够**时允许用积分补，1 比 1。
> 代价是「积分也能买 ¥69 的盲盒」这件事**部分成立**了 —— 家长接受，
> 因为不这样的话，一个积分很多、券很少的孩子在心愿商城里什么都换不了。
> 分账仍然**券优先**：券够的时候一分积分都不动（`planWishRedeem` 有单测钉着）。

## 2. 和「兑换」的区别（用户的核心诉求）

| | 兑换（现有，不动） | 心愿商城（新） |
| --- | --- | --- |
| 位置 | 底栏第 3 格 | **底栏第 4 格** |
| 商品 | **家长自己加的**，已经确认能兑现 | **合作商/运营提供的**，家长要先「开放」 |
| 币 | 积分 + 兑换券混付 | **同样是混付**（v3 起）：券先花，不够用积分补 |
| 兑现方 | 家长本人（给零食、开平板） | **淘宝/天猫/京东/闲鱼** |
| 孩子能做什么 | 直接换 | **只能先表明意向** |

一句话：**兑换是家里的事，心愿商城是外面的事。**

## 3. 商品与分类

分类 tab（横向 chips，可滑动）：`全部 · 盲盒 · 游戏 · 玩具 · 学习 · 美食 · 出行 · 其他`

> 2026-10-29 第三轮：「收藏换成其他，前面再加美食，出行。」⇒ `WishKind` 新增
> `food` / `outing`，`collectible` 的**显示名**改成「其他」（内部名不动）。
> chips 是从 `WISH_KIND_META` 的 key 生成的，加一档就多一个按钮；
> **空分类会真的出现一个点进去什么都没有的按钮**，所以 `wishCatalog.ts`
> 里给这两档各配了样例商品。

**「全部」里游戏盲盒置顶**（用户要求：优先显示游戏盲盒）。

| 类型 | 是什么 | 兑换后发生什么 |
| --- | --- | --- |
| `blindbox` 游戏盲盒 | 随机开出 **1 款孩子还没有的**游戏 | App 内直接解锁，当场开箱 |
| `gamebox` 单个游戏 | **指定**某一款游戏 | App 内解锁那一款 |
| `toy` / `study` / `collectible` | 实物商品 | 家长去外链买，买好回来确认 |

> ⚠️ **`gamebox` 在界面上就叫「游戏」，不叫「盒子 / 指定款」**（用户 2026-10-28 原话：
> 「单个游戏就是游戏 不是盲盒」）。内部字段名保留 `gamebox` 是为了不动数据结构。
> 点进一款游戏时，摆的是**和「设置 → 游戏 → 详情」同一份内容**：手绘图标、版本、
> 适龄 / 一次多久 / 包多大、截图（可点开放大）、练什么、关于这款游戏。
> 只给一颗 emoji + 一句话，家长判断不了该不该让孩子攒券换。

### 盲盒的三条硬约束

1. **池子里只放孩子还没有的游戏**。全都有了就不能买 —— 按钮显示「全都玩过了」，
   不要让人抽到一个空盒。
2. **池子空了要能优雅收场**：随机前先算 `pool ∩ 未拥有`，为空直接拒绝，
   **不要先扣券再发现没得开**。
3. **盲盒不能比盒子便宜太多**。否则所有人都买盲盒、没人买指定款，
   而盲盒的期望成本是一样的 —— 定价上盲盒应当**略便宜**（10~20%），
   而不是便宜一半。这条写在这里是因为它只在数值上看得出来，代码里看不出来。

## 4. 状态机

```
（商品层）locked ──家长定价──▶ open
                                  │
（订单层）wished ──孩子确定兑换──▶ committed ──家长确认──▶ confirmed ──▶ done
   ▲                                  │
   └────────── 取消（退券）─────────────┴──▶ cancelled
```

| 状态 | 谁推进 | 券 | 说明 |
| --- | --- | --- | --- |
| 商品 `locked` | — | — | 家长还没开放。孩子只能「想要这个」 |
| 商品 `open` | 家长 | — | 已定价，孩子可以换 |
| `wished` | 孩子 | 不动 | 只是意向，随时可撤 |
| `committed` | 孩子 | **扣掉** | 已兑换，等家长确认 |
| `confirmed` | 家长 | 不动 | 家长已去外链购买 |
| `done` | 家长 | 不动 | 买好了 / 收到了 |
| `cancelled` | 家长 | **退回** | 买不成、不想要了 |

⚠️ **商品层的 `open` 是「本家庭的设置」，不是商品的全局属性。**
`WishItem` 是常量目录，`open` + `voucherPrice` 存在 `WishOffer` 表里。
不要往常量里写可变状态。

### ⚠️ 数字商品和实物共用这套状态，但**文案必须分叉**

盲盒 / 盒子在**兑换那一刻就交付**（当场开箱、当场装包），实物才要等爸妈去淘宝买。
两者都停在 `committed`，界面上却必须是两句话：

| | 交付时点 | `committed` 的意思 | 界面上该说 |
| --- | --- | --- | --- |
| 盲盒 / 盒子 | 兑换当场（`openedGameId` 就是凭证） | 东西**已经给了**，只差家长收尾 | 「已经放进你的游戏柜了」 |
| 玩具 / 学习 / 美食 / 出行 / 其他 | 家长买完、点「已经买好了」 | 等家长去外链买 | 「等爸妈确认」「确认兑换 · 去购买」 |

判据是 `order.openedGameId`（装包成功才会写），不是 `kind` —— 盒子装包失败
会走 `wishCancel` 退回，那种单子本来就不该显示成「已交付」。

反例（2026-10-28 走查抓到的）：孩子刚开完箱、游戏已经能玩，列表上挂着
「等爸妈确认」，点进详情先撞一道家长密码「确认兑换需要密码」，底下按钮
写着「去购买」。三句话单独看都合法，合起来自相矛盾，而结构断言全绿。

### ★ 家长待办：`wished` 在 👀 里，不在心愿页（2026-10-29，当天改过一次）

家长原话（第一轮）：「现在心愿商城里 已告诉爸爸妈妈，爸爸妈妈如何处理。」
家长原话（第二轮，当天）：「我希望 心愿商城 爸爸妈妈收到心愿，也跟任务一样，
出现在**上边栏的眼睛那**，而不是在心愿商城这里。爸爸妈妈会查看处理。」

改动之前，心愿商城的待办卡**只收 `committed` / `confirmed`** —— 也就是
孩子**已经花掉券**的单子。于是孩子点完「🤍 想要这个」、他那一侧写着
「已经告诉爸妈，等他们定价」，家长那一侧却**一片安静**：没有红点、
没有卡片，商品卡上只是标签从「等爸妈开放」变成「已告诉爸妈」。

第一版把卡摆在**心愿页顶部**；家长当天要求挪进顶栏 👀，理由是「跟任务一样」——
家长已经习惯从 👀 那个红点进去处理所有待办，多一个入口就要多记一件事。

现在两个入口，因为**该做的动作不一样**：

| 状态 | 入口 | 家长要做的 | 出口 |
| --- | --- | --- | --- |
| `wished`（这件商品还没定价） | **顶栏 👀** 的待办队列（`ReviewSheet` 的 `kind: 'wish'`） | 就地定价，或者这次先不换 | `wishSetOffer` / `wishCancel` |
| `committed` / `confirmed` | 心愿页顶部「有 N 单在等爸妈处理」 | 去外链买，或者收尾 | `wishConfirm` / `wishDone` |

⚠️ 合成一张卡的话，文案只能写成「有 N 单等你处理」，等于什么都没说。

⚠️ **第二行不能跟着搬进 👀**。它不是「孩子表了个态」，而是「券已经扣了、
等着你去买」—— 已经成交的单子，处理现场就在心愿页（填收货信息、开外链、
收尾）。搬进 👀 的话，家长点完「确认」那一单就消失了，货却没买。

#### ★★ 判据不是 `status === 'wished'`

家长定完价之后，那条单子**仍然停在 `wished`** —— `wishRedeem` 要等孩子
真的来换才会把它复用并翻成 `committed`。所以「已经回应过」和「还没回应」
在数据上是**同一个状态**。

只按状态算的后果：顶栏红点永远消不掉。家长定完价、孩子还没去换的那段时间，
红点还亮着，点进去却是一件已经开放的商品 —— 一个点不完的数字比没有红点更糟。

判据取「这件商品现在有没有开放价」（`domain/wish.ts` 的 `wishesAwaitingReply`，
顶栏红点和审核队列共用它）。`closedAt` 的行不算开放 —— 家长关掉之后，
那条心愿重新变回「等你回应」是对的。

#### ★ 定价 = 上架（`wishShelf`），而且**就地能换**

家长原话（2026-10-29，两轮 —— 第二轮回过头纠正了第一轮的做法）：

> 「爸爸妈妈已经定好价格的，相当于添加了兑换，应该出现在兑换列表里。」
>
> 「兑换 里的东西都是一样，都能用兑换券或者积分，包括游戏也一样。
> 不需要去心愿商城换。心愿商城只是标明心愿的。」

所以定价之后，那件商品出现在**孩子「兑换」那一格**，但是：

* **不是单独一块**。没有「🛍️ 心愿商城 · 爸妈开放了」这个标题 ——
  它和家里的兑换品排在**同一个分类列表**里（分类固定 `gift`，
  只决定分组标题、不决定付款规则），按价格混排。
* **不是一道门**。第一版做成了「点一下 → `jumpToWish` → 切到心愿页去换」，
  家长当场否掉：那等于在兑换里开一个入口，通往**另一个收银台**。
  现在点「换这个」→「换！」就在这一行扣币、生成订单。
* **同一套付款**。`planRedeemPayment`（券优先、券和积分 1:1、可混付）——
  和家里那几件调的是**同一个函数**，按钮上写的分摊等于实际扣的。
  交付那一步才分岔：盲盒当场揭晓（`BoxView`）、盒子顺手装包、实物留 `committed`
  等家长去外链买。这三条都在 `wishRedeem` 里，界面不重复实现。

`wishShelf` 的四个排除条件一个都不能少：没定价 / 已关闭、已下架、
**已经拥有**（和心愿页共用 `wishOwnedSet`）、盲盒池子开完；
另外 `committed` / `confirmed` 的在走流程也不列（不然等于鼓励孩子换第二遍）。

⚠️ 心愿页因此**不再扣币**：它的详情页只有「想要这个」和「🎁 去「兑换」换」
（后者只是 `jumpToRedeem(itemId)` + 滚到那一行闪一下）。
它现在的职责就是家长说的那句「**只是标明心愿的**」。

⚠️ **`wished` 必须有「不换」这个出口**。没有它，孩子的心愿会永远停在
「等他们回应」—— 他既不能自己撤回，家长也没有拒绝的选项。
走 `wishCancel`（事务内重读状态；对 `wished` **不碰账本**，还没扣过券），
`cancelReason` 写「这次先不换」，孩子**再点进那件商品**就能看到（详情页那句「上次爸妈说：…」）。
（原来这个理由显示在「我许的愿」那一屏 —— 它 2026-10-29 下线了。）

#### 撤回按钮**不进家长闸门**

详情页那个「先不要了」只渲染一次，两种身份共用（家长按是回绝，孩子按是撤回，
落库是同一件事）。它**不在** `needsPin` 分支里面 —— 撤的是孩子自己表的态，
不花钱、不碰账本。放进闸门里的后果是：家长锁一开，孩子后悔了只能干等，
而家长那边根本不知道有个作废的请求还挂着。

同一屏里「定个价」在闸门里、「先不要了」在闸门外 —— 这是**故意**的不对称。

#### 被回绝过要留一句话

商品详情在「🤍 想要这个」下面补一句「上次爸妈说：…」（取最近一条带
`cancelReason` 的 `cancelled`）。没有它，孩子看到的是一个干干净净的
「想要这个」，会以为自己没说过，家长则收到同一个请求第二遍。

⚠️ **只是提示，不是冷却**：仍然允许再点。用时间锁挡住孩子，只会让家长
在不知情的情况下继续收请求。

## 5. 券的扣与退（唯一会碰账本的地方）

```
孩子确定兑换： 券  delta = -voucherPaid, source = 'wish_redeem'（harvestLedger）
             积分 delta = -pointsPaid,  source = 'wish_redeem'（ledger）
家长取消：     券  delta = +vouchersHeld, source = 'wish_refund'
             积分 delta = +pointsHeld,   source = 'wish_refund'
```

`HarvestSource` 里的 `wish_redeem` / `wish_refund` 是 2026-10-28 加的；
`LedgerSource` 里同名的两个值是 2026-10-29 混付时补的（**两边都要有**，
少一边就是「扣了两种、退了一种」）。

### 为什么必须真扣（而不是像积分那样只做门槛）

因为**成交在 App 外面**。券如果不扣，孩子可以同时挂 10 个「已兑换」，
家长每个都要去淘宝买 —— 那是灾难。

### 防重复退款

取消必须在**事务内**先读 `status`，只有 `committed` / `confirmed` 才允许转 `cancelled`。
不要靠按钮 disabled —— 两个标签页同时点会各退一次。

### 券不够怎么办（v3 已改）

**混付**，和「兑换」一字不差：券先花，不够的部分用积分补，1 券 ≡ 1 积分。
（v2 写的是「不混付、只收券」，2026-10-29 家长要求统一，**已作废**。）

- 分账**只有一处实现**：`domain/redeem.ts` 的 `planRedeemPayment`，
  `planWishRedeem` 只是转发。两处各写一遍的话，界面预览和真正扣款会算出两个数，
  差额通常只有几分 —— 孩子的余额看起来就是「莫名其妙少了 1」。
- 两种币**各写一笔账**：券走 `harvestLedger`、积分走 `ledger`，
  source 都是 `wish_redeem` / `wish_refund`；为 0 的那一侧**不写**。
- 订单上同时记 `vouchersHeld` / `pointsHeld`：退款按这两个数原样退，
  只退一种 = 另一半静默蒸发，而且不报错。
- 券和积分**加起来**都不够时按钮是灰的，写「还差 12」（不带「张」——
  差额是两种币合起来算的）。

### 数字商品的「拥有」必须有一份卸载不掉的记录

游戏类商品（盲盒 / 盒子）的交付 = **装包**，而「拥有」一直是从
`installedGames` 派生的。问题是 `uninstallGame` 会把包**和存档**一起删掉
（`clearGameKv`）—— 删完之后这个游戏既不在 `installedGames`，
也不在 `ownedGameIds`（心愿商城不走钻石账本）：

| 后果 | 表现 |
| --- | --- |
| 盒子卡片变回可兑换 | 孩子**再扣一次券**，游戏重装一遍 |
| 盲盒池子把它放回去 | **再开出来一次** |

全程不报错，账面上是两笔合法的 `wish_redeem`。券是真金白银攒的，
卸载一次就白扣一次。

**规矩：**「拥有」= 账本买过 ∪ 现在装着 ∪ **心愿单里兑换到手过的**
（`redeemedGameIdsFrom(wishOrders)`，取 `committed` / `confirmed` / `done`
且带 `openedGameId` 的）。

两处必须用**同一个**派生函数：`wishRedeem` 的闸门、`WishPage` 的
「已经有了」判断。各写一遍就会变成「卡片说能换、点下去被拒」或反过来。

⚠️ 实物**不适用**：同一个玩具买第二次是合理的，所以只有带
`openedGameId`（数字交付）的订单参与计算。

### 取消 = 撤销交易，所以**游戏要一起收回**

不变量只有一条：**券和游戏不能同时到手。**

| | 券 | 游戏 |
| --- | --- | --- |
| `committed` / `done` | 扣着 | 装着 |
| `cancelled` | 退回 | **必须收回** |

不收回会同时踩两个坑：白拿一个游戏；而且取消之后 `redeemedGameIdsFrom`
不再认它（`cancelled` 不算），孩子还能**再兑换一次**。

**收回用 `detachGameKv`（只删 `__bundle` / `__assets`），不是 `clearGameKv`。**
撤销的是这笔交易，不是孩子玩出来的进度 —— 家长点「取消」的动机通常只是
「价格定错了」，不该顺手把存档抹掉。存档留着，将来重新兑换能接着玩。

⚠️ 界面上**必须先说清楚**（「取消会把游戏收回，进度保留」），否则游戏
从孩子的游戏柜里消失而家长毫无预期。

⚠️ `wishRedeem` 装包失败时也走 `wishCancel`：那时 `gameKv` 里没有包，
`detachGameKv` 删 0 行，无副作用 —— 别为这条路再分叉出一个「不收回」的参数。

## 6. 外链与码

### 外链

商品带 `buy_url`（淘宝/天猫/京东/闲鱼），由运营在 tf-admin「商城」列表里配。

> ★ **第七轮（2026-11-06）定稿**：这条链接**两端都下发**，而且它是
> **「去购买」按钮存不存在的唯一判据** —— 后台没配，孩子端和家长端都
> **不摆这颗按钮**（用户原话：「如果没有就不显示」）。
>
> 第六轮之前孩子那颗按钮永远在，链接是客户端**现拼**的淘宝搜索页
> （`wishCatalog.ts` 的 `wishBuyUrl`），和后台配的东西毫无关系 ——
> 于是「运营没配」和「配了」在界面上长得一模一样。那一套兜底这一轮**删掉了**。

点了就是 `window.open(buyUrl)`，App 不知道也不关心成交结果 ——
家长回来点「已经买好了」才算 `done`。

⚠️ 文案必须写清楚 **「App 不代收货款」**。本项目最忌讳界面承诺它做不到的事。

### 码（P2，✅ 2026-10-29）

游戏之后也会上淘宝：用户付款 → 拿到码 → 在 App 里输码解锁。

- `MallSource` 里**已经留了 `redemption_code`**
- `purchasedIdsFrom()` 必须一起改 —— 它对 `redemption_code` **不看 delta**
  （码解锁的 delta 恒为 0，写 0 是事实）。只看 `game_purchase && delta < 0`
  的话，码解锁了游戏却不显示「已拥有」，而且**零报错**
- 码表只存 `sha256`，不存明文；已用码进 `wishCodes` 表防重

#### 实现要点（改这块之前先读）

| 件 | 在哪 | 干什么 |
| --- | --- | --- |
| 格式 | `src/domain/gameCode.ts` | 6 位 Crockford Base32（去掉 I L O U），手输友好：`I`/`L`→`1`、`O`→`0` |
| 码表 | `src/games/codeTable.ts` | **生成文件**，`{ sha256: gameId }`。反推不出明文 |
| 查表 | `src/games/codeLookup.ts` | 归一化 → sha256 → 查表 |
| 发码 | `scripts/mint-codes.mjs` | 写码表 + 明文清单（`scripts/_codes-*.txt`，gitignored），**写完自检** |
| 兑换 | `useApp.redeemGameCode` | 查重 → 记 `wishCodes` → 记账本（delta 0）→ 装包 |

**四件「不烧码」的事**：格式不对 / 表里没有 / 本机用过 / 已经有了 /
这个版本没有这款游戏。码是一次性资源，浪费一张少卖一张。

**装包失败要退码**：事务提交之后才装包（网络 + 执行不能塞进 Dexie 事务），
装失败就把 `wishCodes` 和账本那两行删掉。否则孩子拿到「装包失败」而码已经没了。

⚠️ **防重只在本机**。没有账号、没有服务器 ⇒ 文案里不许写「一次性」。
换台设备可以再用一次。

   孩子换到手的东西过一天就查不到「我到底换过没有」。

家长密码（2026-10-28 在详情页右上角那个入口上踩过一次）。

### 价格怎么显示（财商教育）

孩子端**显示参考价**，但必须满足两条：

1. **和券价不在同一行**，中间隔一层（分隔线 / 留白）
2. 价格旁写 **「家长支付」**

理由：`80 张` 和 `¥69` 并排，孩子会自己算出 1 张 ≈ ¥0.86 —— 这是算术本能，
挡不住。能挡住的只有**归属**：「我攒券，爸妈付钱」。两个主体、两件事，比率就不成立。

绝对不许出现：「1 张 = ¥x」「你省了 ¥x」。

## 9. 隐私

收货人 + 手机 + 家庭地址，绑在儿童账号上 = 敏感个人信息。

1. **备份里不能有 `ship`**。`exportBackup()` 是逐表列举的，新表默认不导出 ——
   真实风险是有人为了保住兑换历史把 `wishOrders` 整表塞进去，顺手带出地址。
   导出前 strip 掉 `ship`，只留 `region` + `phoneTail`。备份 `version` 2 → 3。
   > 2026-10-30 补：`wishCodes`（P2 加的那张表）当初**导出和清空都漏登记** ——
   > 清空全部数据、或恢复一份「兑换之前」的备份之后，游戏没了而码还标着「用过」
   > ⇒ 那张实体卡作废，界面只说「这个码已经用过了」。现在两个方向都登记，
   > 备份 `version` 3 → 4，并且 `useApp.test.ts` 加了**覆盖面闸门**：
   > 枚举 `db.tables`，哪张表没进备份 / 没被清空就直接红。
2. **备份里也不能有家长 PIN**（2026-10-30 补）。`settings.parentPin` 是**明文** 4 位，
   而 `settings` 整份进备份 —— 每导一次，家长锁的密码就跟着 JSON 离开设备。
   现在导出剥掉（`stripParentPin`，顶层 `settings` 和 `meta.settings` **两处**都要剥），
   导入不认文件里的值（只保留本机原来那个）。4 位数字的哈希也挡不住爆破，
   所以不是「换个哈希」，是**根本不进文件**。
3. **完成 30 天后自动抹除**：`ship` 降级成 `{ region, phoneTail }`。启动时扫 `purgeAfter`。
3. **不进日志 / toast / 埋点**。
4. **孩子端完全看不到** `ship`。`buy_url` 自第七轮起**两端都下发**
   —— 它是运营配的公开商品页，不是隐私。但仍然**只用来 `openExternal`**：
   不写进 `href`、不进日志、不进埋点（否则孩子一点就把外链暴露在 DOM 里）。

### 12.0 招商那一句被读错过一次（留在这儿当教训）

第一版把招商做进了「📜 兑换记录」的底部，还配了一张「称呼 / 联系方式」表单。
用户当场纠正：

> 「在 心愿右上角 把兑换记录 去掉 换成招商按钮。点开 看到招商合作。
> **不是在兑换/兑换记录里显示**。另外家长申请 **不是 邀请商家 而是分享让其他家长使用**。
> **点申请即可**。不需要填 称呼 这些。因为会根据当前账号，申请。之后会接入服务端的。」

三处都错在「把一句需求读成了另一句」：

| 用户说的 | 第一版做的 | 正确的 |
| --- | --- | --- |
| 心愿**右上角**换成招商按钮 | 兑换记录底部一张卡 | 心愿页头部右端（原「我许的愿」那个位置） |

| **点申请即可** | 一张三格表单 | 一键提交，身份取当前账号 |

判据因此有一半是**反向**的：入口在头部（几何量：`top < 120` 且贴着标题行右端）、
兑换记录里**没有** `[data-merchant-entry]`、招商页里**一个 `input/textarea` 都没有**。
只写正向断言的话，「做错地方」照样全绿 —— 第一版就是这么过的闸门。

### 12.2 招商：两路申请，一键提交，一套状态机

入口在**心愿商城右上角**（原来「我许的愿」的位置）。

```
心愿商城 ──[🤝 招商]──> 招商页
                          ├─ 👤 家长申请   分享给其他家长，别人用起来你拿分成
                          └─ 🏪 商家申请   自己上架商品
                               └─ [申请] ──> status: 'pending'（无表单，身份取当前账号）
                                              └─ 后端回填 ──> 'approved' + adminUrl
                                                               └─ 「↗ 打开后台」
```

**为什么没有表单**：身份由账号体系决定（用户原话「因为会根据当前账号，申请」）。
表单里那些字段后端拿不到，用户还要白填一遍。所以只发一个
「谁、什么时候、申请了哪一路」。

**2026-10-29 晚：后端接上了**（`tf-platform-api` 的 `/api/merchant/*`）。
上面那张图里「后端回填」那一半现在是真的，不再是留给未来的注释：

- 客户端 `applyMerchant(role)` **只发 `role`**；`name` / `contact` 由服务端
  从账号取（客户端拿到的手机号是 `138****8000`，拼不出真号码）。
- 状态**不再存本地**。`settings.merchantApps` 已删除 ——
  两份状态一定会对不上，而对不上的表现是「界面写着审核中、后台其实已经通过了」，
  这种不一致没有任何测试查得出来。
- `admin_url` **只在 `approved` 时由服务端返回**。客户端不判断「这个状态该不该
  渲染链接」—— 判断错了就是一个写着「已通过」、点进去 404 的按钮。
- 未登录时这一屏**只做一件事**：说清楚为什么登录，给一个登录按钮。
  **不偷偷存本地假装成功** —— 家长会以为申请已经发出去了。

## 13. 5 连开盲盒（2026-11-04）

用户原话：「加一个一次开 5 款的盲盒，**已经解锁的不计算**」。

### 13.1 商品与字段

| 位置 | 字段 | 说明 |
| --- | --- | --- |
| `wish_item` | `unlock_count` | 一次开出几款。`1` = 老的单开，`5` = 5 连开 |
| `wish_order` | `opened_game_ids` | 这一单**实际开出的全部**（JSON 数组） |
| `wish_order` | `opened_game_id` | 仍然是**第一个**（老代码/老数据只看这一个） |

商品 id 两端**必须一致**：客户端 `games/wishCatalog.ts` 的
`WISH_BLINDBOX5_ID = 'wish-blindbox-5'`，服务端 `seed/wish_catalog.go` 的
`WishBlindBox5ID`。不一致的症状是「本地有这个商品，服务端说没有这件商品」，
孩子点兑换只会收到一句「商品不存在」。

5 连开的池子**照抄**单开（全部随包游戏）。「已解锁的不计算」不是靠池子实现
—— 池子里写「剩下的那几款」就等于把某个家庭的拥有关系写进了全站常量。

### 13.2 三条口径（少一条就是静默错）

1. **已拥有的不占名额**：先把孩子已拥有的从池子里减掉，再从剩下的里面抽 N 款。
   所以「有 7 款、已拥有 4 款」时 5 连开**换不了**（只剩 3 款）。
2. **剩余不足 N 款 ⇒ 整单拒绝**，不是「有几款给几款」。
   卖的是 N 款的价，给少了就是缺斤少两；更糟的是「扣完钱才发现开不了」。
   服务端在**扣款之前**判（`len(picks) < n` ⇒ `WishBlindBoxEmpty`），
   客户端在**扣券之前**判（`picked.length < need` ⇒ 一句「没解锁的游戏不够 5 款啦」）。
3. **取消 = 全部收回**。只看 `opened_game_id` 会让另外 4 款白送，
   而且不报错（账本只看 delta 之和，界面只会说「取消成功、券退了」）。

### 13.3 ★★ 取消时收回必须**硬删**（这次真踩到的 bug）

`user_game` 上有 `uk_uid_game (uid, game_id)` 唯一索引，而软删只是写一个
`deleted_at` —— **那一行仍然占着唯一索引**。于是：

```
兑换 → 取消（软删）→ 再兑换到同一款
  ⇒ GrantGameWithTx 的 ON CONFLICT DO NOTHING 静默不写
  ⇒ 孩子付了钱、界面说「兑换成功」，库里一条拥有关系都没有
```

实测（`TestWishRedeemAgainAfterCancelGetsGamesBack`）：5 连开取消后再兑换，
5 款**只回来 1 款**，回来的那款是「上一单恰好没开出来」的那个。
单开盲盒同样中招，只是概率低、不容易被发现。

修法：`RevokeGameWithTx` 用 `Unscoped()` 硬删（只删 `user_game` 那一行，
**不删存档** `game_kv` —— 存档是孩子的进度，不是交易凭据）。

### 13.4 客户端两处判据改了

- **售罄**：从「池子空了」改成 `blindBoxSoldOut(item, owned)`
  （剩余 < 这一盒要开的款数）。5 连开只剩 2 款时也必须显示售罄，
  否则点进去必然被拒 —— 「点了没反应」和「卖光了」是两件不同的事。
- **装包**：`gameIds` 逐个装，**任何一款失败就把整单退回去**
  （`wishCancel` 会把已装的那几款一起摘掉）。只装第一个的话，
  孩子付了 5 份的钱、拿到 1 款，而界面说「兑换成功」。
- **揭晓**：`BoxView` 从「接一个 `gameId`」改成「接整个清单」。
  只接第一个的话，库里 5 款都对、屏幕上只揭晓 1 款 ——
  孩子以为「付了 5 份的钱只开出 1 款」，而任何结构断言都不会红。
  `wishRedeem` 的返回值也因此多了 `gameIds`（`gameId` 保留给老调用方）。

### 13.5 后台

心愿商城页的「盲盒」商品多了一个「一次开出几款」（`unlock_count`，1~20）。
非盲盒保存时**一律写回 1** —— 不然「盲盒改成游戏盒子」之后这个字段还留着 5，
下一个把商品改回盲盒的人会莫名收到 5 连开。

⚠️ 备份里**剥掉**这个 key：它是后台配置的本地缓存，不是孩子挣到的东西。
跟着备份跑到另一台设备上，运营后来清掉的链接会复活（点进去 404），
而下次拉取之前没人知道。

### 6.4 家长定「能兑换几次」

`WishOffer.oneTime`（服务端 `wish_offer.one_time`）：

- `true` = 兑换成功那一刻**自动关闭**这一行（`closed_at` 置为当前时间）：
  商品从「兑换」列表消失，心愿商城回到「我想要」，孩子可以重新许愿、家长重新定价。
- `false` / 不填 = 可以反复兑换，「兑换」列表里一直留着，并显示「已兑换 N 次」。

入口有两个，**两个都要有**：

| 入口 | 文件 | 说明 |
| --- | --- | --- |
| 顶栏 👀 家长待办 | `features/parent/ReviewSheet.tsx`（`WishReviewCard`） | 家长审核「我想要」时定券数 + 一次 / 多次 |
| 心愿商城 → 家长定价页 | `features/wish/WishPage.tsx`（`OfferView`） | 改价时也能改这个开关 |

默认值：`gamebox` / `blindbox` = 一次性（码只能用一次）；实物 = 可重复。

⚠️ 服务端 `WishSetOfferReq.OneTime` 是 **`*bool`**：`nil` = 保持原值，
显式 `false` = 改成可重复。用 `bool` 的话，「关闭商品」（`voucher_price = 0`）
那条请求会顺手把一次性标记冲成 `false`，家长下次重新开放时语义就悄悄变了。

### 6.5 一次性关闭必须和兑换在**同一个事务**里

服务端 `WishService.Redeem` 在 `UpdateOrderCAS` 成功之后，同一个 `tx` 里调
`CloseOfferWithTx` 写 `closed_at`。

不能交给客户端再发一次 `set-offer(0)`：那次请求失败时券已经扣了、商品却还挂在
兑换列表上 —— 孩子能再换一遍，而且两边都不报错。本地 Dexie 模式同理，
`wishRedeem` 的 `db.transaction` 把 `db.wishOffers` 一起纳进来了。

### 6.6 「可兑换」只负责送人，不扣币

心愿商城这一页**从来不扣币**（第 2 节那条设计还在）。所以「可兑换」不再调
`wishRedeem`，而是 `jumpToRedeem(item.id)` —— 跳到「兑换」那一格并高亮那一行。

判据（`WishPage.test.tsx`）：

```ts
expect(useApp.getState().pendingRedeemItem).toBe('wish-dino')
expect(useApp.getState().harvestBalance).toBe(before)   // 没扣
expect(useApp.getState().wishOrders.length).toBe(0)     // 没生成订单
```

### 6.7 兑换列表显示「已兑换 N 次」

`RedeemSheet.tsx` 按 `wishOrders` 统计，**只数成交过的**：
`committed` / `confirmed` / `done`。`wished`（还没成交）和 `cancelled` 不算。

⚠️ 拿 `confirmed` 当「成交过」的例子写测试会翻车：它算**在走流程**，
`wishShelf` 会把整行排除掉，测试里那一行根本不出现。

### 6.8 一次性兑换完、单子还停在「等爸妈买」怎么办

用户选了「立刻变回『我想要』」。于是卡片状态判据改成**先看 offer 在不在**：

```ts
if (offerExists) {
  if (order?.status === 'committed' || order?.status === 'confirmed') return '已兑换'
  return '可兑换'
}
```

offer 被关掉（`closedAt` 有值）⇒ 落到默认的 `🤍 我想要`。

但这时那单可能还没走完，再点「我想要」会撞上进行中的单子。所以 `wishExpress`
（本地 / 在线两条路）都要给反馈：

```
这一单还在等爸妈处理 / 处理完了才能再许愿
```

否则就是「点一下什么都没发生」—— 第四轮踩过的那个坑。

## 第七轮：外链只认后台配置（2026-11-06）

用户原话：「有没有去淘宝的按钮，根据后台礼品有没有配置链接（淘宝、京东等等），
如果没有就不显示。」

### 7.1 服务端

`WishItemView` 新增 `buy_url` / `buy_label`（`omitempty`），由 `buildItemView`
从 `wish_item` 带出来。`WishItemDetailResp` 里那份**重复的**同名字段删掉
（外链跟着视图走，两端一样）。

`WishItem.BuyURL` 上的 `json:"-"` **保留**：那个结构体不直接序列化，
对外的字段在视图上。两处别各写一套口径。

判据（`wish_buy_link_srv_test.go`）：
- 配了就下发（孩子视角 `Detail(isParent=false)` 也要有）
- 没配就是空串 —— **空串是判据，不是「没数据」**。服务端要是顺手补一条默认
  淘宝搜索页，那条断言就是最后一道闸。

### 7.2 客户端

- `ServerWishItemView` 加 `buy_url` / `buy_label`
- `pull.ts` 建 `Record<itemId, {url,label}>` → `saveWishBuyLinks`（写 `meta`），
  **整份替换**、**只在拉取成功时写**
- `store.wishBuyLinks` 由 `refresh()` 从 `meta` 读
- `wishCatalog.ts` 删掉 `wishBuyUrl` / `wishBuyLabel` / `taobaoSearch`，
  以及 8 件实物商品上的 `buyUrl` / `buyLabel`（16 行）

### 7.3 本地版（`VITE_APP_MODE=local`）没有购买按钮

本地版没有服务端 ⇒ `wishBuyLinks` 恒为空 ⇒ 三处按钮都不渲染。
**这是对的**：没有后台，就没有「后台配的链接」。别为了让本地版「看着完整」
把目录兜底加回来 —— 那正是这一轮删掉的东西。
